# RISK-REGISTER.md

Synthesis of the 17 discovery reports in `docs/discovery/` (A–O) and the ~350 files in
`findings/`. Every row cites `file:line` from the working tree at `bef5f89`. Severity is the
discovery corpus's own scale: **blocker** | **major** | **minor** | **spec** (speculative).

Owner workstreams: **W1** transport (streamer core, WebRTC, session, cloud) · **W3** Windows
capture/encode · **W4** AMD · **W5** macOS capture/encode · **W6** macOS
permissions/hosted-network/virtual-display · **W7** macOS audio · **W8** Windows + core audio ·
**W9** Windows utils (driver IPC, networking, compat) · **W10** input · **W11** client page ·
**W12** desktop UI · **W13** shell/CLI/build/docs · **W14** AirPlay · **W15** tests.

`P-macos-dyld-audit.md` was **not present** when this register was written; §5 records the
verdict as *pending* and names the one command that settles it.

## 12. Concurrency

**Headline: no `MutexGuard` is held across an `.await` anywhere in the tree.** All five reports
that looked for it (A, C, D, G, K) confirm the same, and the compiler backstops it in every `Send`
context because `MutexGuard` is `!Send`. The two intentional async locks are exactly the two
`CLAUDE.md` names: `DISPLAY_CORRELATION_LOCK` (`server.rs:94`) and `receive_error: RwLock<…>`
(`driver_ipc/client.rs:35`). The real hazards are the three the rule does *not* catch: **guards
held across blocking calls**, **guards held across synchronous callbacks**, and **blocking OS work
on tokio workers**.
