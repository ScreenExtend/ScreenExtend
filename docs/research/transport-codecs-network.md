# Transport, codecs and the network stack

## 1. Question

What is the lowest-latency way to move encoded video and input between a Rust host and a browser
client, on LAN first and cloud/TURN second — and is H.264 still the right codec?

Sub-questions: where a receiver-side insertable-streams transform actually sits in the browser's
receive pipeline; how to build a pacer and a delay-based bandwidth estimator on top of
`webrtc-rs`, which ships neither; whether WebTransport over HTTP/3 is now a viable tier; how to
recover from loss without paying a keyframe every time; whether HEVC or AV1 beats H.264 here; what
socket- and radio-level tuning is reachable; and how to keep input off the video's critical path.

Facts already established in `docs/research/competitors-open-source.md` and the `findings/`
queue — webrtc-rs 0.17.1 has no pacer and no congestion controller, the TWCC *sender* interceptor
is never registered, `enable_sender_rtx` is false, playout-delay(0,0) and `jitterBufferTarget=0`
are already set, the RTP payload MTU is fixed at 1188 — are taken as given and built on, not
re-derived.

---

## 2. Findings

### 2.1 Where the receiver-side encoded transform sits — it is *before* the jitter buffer

This is the load-bearing fact for the whole client design, and it is verifiable in Chromium's
source. `RtpVideoStreamReceiver2::OnAssembledFrame` — the function the packet buffer calls once it
has reassembled a complete frame from its RTP packets — branches like this
([rtp_video_stream_receiver2.cc](https://chromium.googlesource.com/external/webrtc/+/refs/heads/main/video/rtp_video_stream_receiver2.cc)):

```cc
if (buffered_frame_decryptor_ != nullptr) {
  buffered_frame_decryptor_->ManageEncryptedFrame(std::move(frame));
} else if (frame_transformer_delegate_) {
  frame_transformer_delegate_->TransformFrame(std::move(frame));
} else {
  OnCompleteFrames(reference_finder_->ManageFrame(std::move(frame)));
}
```

The receive path is:

```
RTP packet
  → RtpVideoStreamReceiver2::OnReceivedPayloadData
  → NackRequester (loss detection, NACK generation)     ← still runs
  → PacketBuffer::InsertPacket / FindFrames             ← waits for all packets of the frame
  → OnAssembledFrame
      ├─ frame_transformer_delegate_->TransformFrame()  ← INSERTABLE STREAMS HOOK
      └─ (otherwise) RtpFrameReferenceFinder::ManageFrame
           → VideoReceiveStream2::OnCompleteFrame
             → FrameBuffer  ← THE JITTER BUFFER: inter-frame reordering, VCMTiming,
                              playout-delay honouring, render-time scheduling
             → decoder
```

The transform is invoked in the `else if` branch, i.e. **instead of** entering the reference finder
and the frame buffer, not after them. Consequences, all of which follow directly:

1. **The WebCodecs path genuinely bypasses the jitter buffer.** There is no de-jitter delay, no
   playout-delay wait, no render-time scheduling. The only queuing left upstream is packet-level
   reassembly in `PacketBuffer`, which is exactly the irreducible "wait for the last packet of this
   frame (and for a NACK repair if one is missing)".
2. **`playoutDelayHint`, `jitterBufferTarget`, and the sender-side `playout-delay` RTP header
   extension are all no-ops on the WebCodecs path.** All three are consumed by `VCMTiming` /
   `FrameBuffer`, which the frames never reach because ScreenExtend's worker reads
   `transformer.readable` and never writes to `writable`. They still matter — a lot — on the
   `<video>` fallback path.
3. **NACK still works.** `NackRequester` lives at the RTP packet level in
   `RtpVideoStreamReceiver2`, upstream of the branch. Loss is still detected and repaired.
4. **PLI does not happen by itself.** Keyframe requests are generated by the decoder /
   `VideoReceiveStream2` when it cannot decode; that machinery never sees a frame. Hence
   `RTCRtpScriptTransformer.sendKeyFrameRequest()` exists at all, and hence a client that cannot
   call it can never ask for an IDR (already filed as
   `findings/major-client-no-keyframe-request-on-chrome.md`).
5. **Receive-side timing stats are unavailable on this path.** `jitterBufferDelay`,
   `jitterBufferTargetDelay`, `totalProcessingDelay`, `totalDecodeTime`, `framesDecoded`,
   `framesReceived`, `totalAssemblyTime` and `framesAssembledFromMultiplePackets` are all
   incremented from `VideoReceiveStream2::OnCompleteFrame` / the frame-buffer timing callbacks
   ([webrtc-stats definitions](https://www.w3.org/TR/webrtc-stats/)). Expect them to be zero or
   absent while a transform is consuming frames. `packetsReceived`, `bytesReceived`, `packetsLost`,
   `nackCount` and the `candidate-pair` stats are RTP-level and still work — which is why the
   client's `handleRenderCount` liveness check on `bytesReceived` (`static/index.html:748-758`) is
   correct and the DEBUG log's `framesReceived`/`framesDecoded`/`pliCount` line
   (`index.html:890-910`) probably prints zeros. *(Mechanism verified from source; the exact set of
   zeroed counters must be confirmed empirically in `chrome://webrtc-internals`.)*

**Firefox and Safari sit in the same place.** Both embed libwebrtc for the RTP receive path, so
the hook is the same `OnAssembledFrame` branch. What differs is only which API exposes it.

| API | Chrome / Edge | Firefox | Safari / iOS |
| --- | --- | --- | --- |
| `RTCRtpReceiver.transform` (`RTCRtpScriptTransform`) | **141** | 117 | 15.4 |
| `RTCRtpScriptTransformer.sendKeyFrameRequest()` | **141** | 117 | 15.4 |
| `RTCRtpScriptTransformer.generateKeyFrame()` (sender side) | not supported | 117 | 15.4 |
| `RTCRtpReceiver.createEncodedStreams()` (legacy, non-standard) | 86 | never | never |
| `RTCRtpReceiver.jitterBufferTarget` | 124 | 115 | **27** |
| `RTCRtpReceiver.playoutDelayHint` | Chromium-only, non-standard | — | — |

Sources: [MDN browser-compat-data `api/RTCRtpReceiver.json`](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/RTCRtpReceiver.json),
[`api/RTCRtpScriptTransformer.json`](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/RTCRtpScriptTransformer.json),
[MDN `sendKeyFrameRequest`](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpScriptTransformer/sendKeyFrameRequest)
(Baseline since October 2025).

`jitterBufferTarget` semantics ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/RTCRtpReceiver/jitterBufferTarget)):
milliseconds, `RangeError` outside 0–4000, and it only *influences* the UA target — the UA remains
free to move between its own min and max at any time, and the getter returns what you set, not what
the UA chose. So it is a hint, not a setting, and reading it back proves nothing.

**`getStats()` cost.** On the client, `RTCPeerConnection.getStats()` is a promise that hops to the
network/worker thread, collects every stats object for every transceiver, sender, receiver, ICE
candidate and candidate pair, and materialises a `RTCStatsReport` map — it is not a cheap accessor,
and it allocates per call. ScreenExtend's client calls it every 2 s in the liveness path
(`index.html:748-753`) plus every 1 s in DEBUG (`index.html:890`). That is fine. The host side is
the problem: `spawn_bitrate_driver` calls `pc.get_stats()` every 120 ms per session
(`webrtc_session.rs:40,873,883`), and webrtc-rs's collector walks all transceivers/senders/
receivers under async locks and `format!`s a fresh `String` id per entry — already filed as
`findings/speculative-webrtc-get_stats-polled-8-times-a-second-per-session.md`. The underlying
`fraction_lost` / `round_trip_time` come from RTCP Receiver Reports at ~1 Hz, so seven of every
eight polls re-read the same numbers.

**What to use for one-way delay.** From the W3C stats spec, per frame:

- `jitterBufferDelay / jitterBufferEmittedCount` — time in the jitter buffer.
- `totalProcessingDelay / framesDecoded` — first RTP packet received → frame decoded. This is the
  single best receive-side latency number.
- `totalAssemblyTime / framesAssembledFromMultiplePackets` — first packet → last packet of a frame.
  This isolates *network burst spread + NACK repair* from everything else, and is the metric that
  will move when the pacer lands.
- `totalDecodeTime / framesDecoded`, `totalInterFrameDelay`, `freezeCount`, `pauseCount`.

All of these are frame-buffer-derived, so on ScreenExtend's fast path they are unavailable and the
client must compute latency itself from the RTP timestamp (which it already tries to do, with a
broken epoch — `findings/major-client-no-glass-to-glass-telemetry.md`). On the `<video>` fallback
path they are all available and currently unused. Chrome M145 is also proposing
`VideoFrame.metadata().rtpTimestamp`
([chromestatus](https://chromestatus.com/api/v0/features?q=WebCodecs)), which would give the
fallback path the same host-clock delta the fast path computes.

### 2.2 Send-side pacing and BWE in Rust

**Why pacing matters, quantified.** libwebrtc's own
[Paced Sending doc](https://chromium.googlesource.com/external/webrtc/+/master/modules/pacing/g3doc/index.md)
gives the arithmetic: a 5 Mbps 30 fps stream, sent unpaced, is *"a burst of 167 Mbps every 33 ms"*,
and *"it is quite common that video encoders overshoot the target frame size in case of sudden
movement especially dealing with screensharing. Frames being 10x or even 100x larger than the ideal
size is an all too real scenario."* ScreenExtend is a screensharing encoder writing exactly such
bursts (`webrtc_session.rs:527-545`).

Useful constants from
[`modules/pacing/pacing_controller.cc`](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/pacing/pacing_controller.cc):
`kMaxDebtInTime = 500 ms` (the leaky bucket may not accumulate more than half a second of debt),
`kMaxElapsedTime = 2 s`, `kMinSleepTime = 1 ms`, `kCongestedPacketInterval = 500 ms`,
`kTargetPaddingDuration = 5 ms`. Priority order in the queue is audio, then retransmissions, then
video/FEC. The pacing rate is `kDefaultPaceMultiplier = 2.5 ×` the target bitrate.

Stadia's measured wire behaviour is the shape to aim for: RTP packets arrive in batches one frame
interval apart (~16.67 ms), and *within* a frame period they are *"grouped in 2-millisecond
intervals"*, roughly 6 groups of 7–9 packets for 1080p
([Carrascosa & Bellalta](https://ar5iv.labs.arxiv.org/html/2009.09786)).

**A minimal correct pacer for this codebase.** ScreenExtend packetizes by hand, so the pacer is
~40 lines in the writer task and needs no library:

```
per session:  target_bps: Arc<AtomicU32>          // written by spawn_bitrate_driver
per frame:
  let pkts   = payloads.len();
  let rate   = 2.5 * target_bps as f64 / 8.0;                 // bytes/s
  let budget = min(frame_interval * 0.6, Duration::from_millis(8));
  let group  = 8;                                             // Stadia's observed sub-burst
  let step   = budget / ((pkts + group - 1) / group).max(1);
  let mut deadline = Instant::now();
  for (i, payload) in payloads.enumerate() {
      write(...);
      if i % group == group - 1 {
          deadline += step;                       // token-bucket variant: += bytes/rate
          if deadline > frame_deadline { break }  // never delay past the next frame
          tokio::time::sleep_until(deadline).await;
      }
  }
```

Three invariants that make the difference between a pacer and a regression: (a) never delay a
packet past its own frame interval — if the previous frame's spread has not finished when the next
frame arrives, flush and abandon; (b) burst floor of ~2 packets so small P-frames are untouched;
(c) `tokio::time::sleep_until` on a per-session deadline, never `interval`, never
`std::thread::sleep`, and no `std::sync::MutexGuard` held across it (`CLAUDE.md`'s rule). Sunshine
uses the same shape — `ratecontrol_packets_in_1ms = giga::num * 80/100 /1000 /blocksize /8`, then
`timer->sleep_for(due - now)` — and batches sends at 64 KB or 64 packets *"to avoid Windows
SO_SNDBUF bypass"* (`LizardByte/Sunshine`, `src/stream.cpp`).

**The bandwidth-feedback situation is worse than "no TWCC" — and better than it looks.**

Reading Chromium's
[`receive_side_congestion_controller.cc`](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/receive_side_congestion_controller.cc):

```cc
if (has_transport_sequence_number) {
  // Send-side BWE.
  transport_sequence_number_feedback_generator_.OnReceivedPacket(packet);
} else {
  // Receive-side BWE.
  MutexLock lock(&mutex_);
  PickEstimator(packet.HasExtension<AbsoluteSendTime>());
  rbe_->IncomingPacket(packet);
}
```

The decision is **per packet**, on whether the transport-wide sequence number extension is actually
present on the wire — not on what the SDP negotiated. ScreenExtend negotiates the extension and
never stamps it, so every video packet takes the `else` branch and Chrome runs a *receive-side*
estimator: `RemoteBitrateEstimatorAbsSendTime` if `abs-send-time` is present, otherwise
`RemoteBitrateEstimatorSingleStream`. Because ScreenExtend also advertises `goog-remb`
(`webrtc_session.rs:86-89`), **Chrome is almost certainly already sending REMB feedback that the
host silently discards** — the RTCP read loop at `webrtc_session.rs:472-483` only downcasts
`PictureLossIndication` and `FullIntraRequest`.

REMB cadence: `RembThrottler` throttles small changes to a 200 ms window and sends immediately when
the estimate *decreases*
([remb_throttler.h](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/remb_throttler.h)) —
i.e. a decrease arrives within one RTCP interval, far faster than the ~1 Hz Receiver Report the
current controller waits for.

Everything needed to consume it is already in the dependency tree:
`rtcp-0.17.1/src/payload_feedbacks/receiver_estimated_maximum_bitrate/` defines
`ReceiverEstimatedMaximumBitrate { sender_ssrc, bitrate: f32, ssrcs }`, and its
`destination_ssrc()` returns `self.ssrcs` — which the browser fills with the media SSRC, so the
packet is routed to `rtp_sender.read()` by the SRTCP session's destination-SSRC dispatch
(`webrtc-srtp-0.17.1/src/session/mod.rs:153-156`). `rtp-0.17.1` also has
`HeaderExtension::AbsSendTime`, so stamping it costs one more entry in the array already passed to
`track.write_rtp_with_extensions` (`webrtc_session.rs:505-539`).

**If you want real send-side TWCC instead**, webrtc-rs already ships the pieces and even the
convenience function:

- `webrtc::api::interceptor_registry::configure_twcc_sender_only(registry, media_engine)` is
  **public** (`webrtc-0.17.1/src/api/interceptor_registry/mod.rs:106-129`) and registers the
  header extension plus `twcc::sender::Sender`. `register_default_interceptors` calls
  `configure_twcc_receiver_only` instead, which is why the extension is negotiated but never
  stamped. So the fix is: `configure_nack` + `configure_rtcp_reports` +
  `configure_twcc_sender_only`, dropping the receive-only variant from a send-only peer connection.
- The Sender interceptor stamps `TransportCcExtension { transport_sequence }` per RTP write and
  is a no-op if the extension ID was not negotiated
  (`interceptor-0.17.1/src/twcc/sender/mod.rs:78-107`,
  `.../sender/sender_stream.rs:26-38`). It composes with the app's own
  `write_rtp_with_extensions`, since it only calls `header.set_extension`.
- `rtcp-0.17.1/src/transport_feedbacks/transport_layer_cc/` gives you
  `TransportLayerCc { sender_ssrc, media_ssrc, base_sequence_number, packet_status_count,
  reference_time, fb_pkt_count, packet_chunks, recv_deltas }`, with
  `TYPE_TCC_DELTA_SCALE_FACTOR = 250` — `RecvDelta.delta` is already in **microseconds**, and
  `reference_time` is in 64 ms units. `destination_ssrc()` returns `media_ssrc`, so like REMB it
  arrives on the existing `rtp_sender.read()` loop.
- **The missing half**: nothing exposes which transport-wide sequence number was assigned to which
  packet, so send timestamps cannot be correlated. `Sender::next_sequence_nr` is private. The fix
  is to write a ~60-line interceptor of our own that does what `twcc::sender::Sender` does *and*
  records `(seq, Instant)` into a shared ring the RTCP reader can join against. The `Interceptor`
  trait and `Registry::add` are public and already imported by `webrtc_session.rs:14`.

**The estimator.** Google's own delay-gradient algorithm, small enough to reimplement, from
[`trendline_estimator.cc`](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/trendline_estimator.cc):

- Per packet group: `delta_ms = recv_delta_ms - send_delta_ms`; accumulate; smooth with
  `smoothed_delay = 0.9 * smoothed_delay + 0.1 * accumulated_delay`.
- Least-squares slope over a **20-packet window** (`kDefaultTrendlineWindowSize`).
- `modified_trend = min(num_deltas, 60) * trend * 4.0` (`kDefaultTrendlineThresholdGain`).
- Adaptive threshold: `threshold += k * (|modified_trend| - threshold) * dt_ms`, with
  `k_up = 0.0087`, `k_down = 0.039`, `kMaxAdaptOffsetMs = 15.0`, clamped to `[6, 600]` ms.
- `Detect()`: overusing if `modified_trend > threshold` sustained for
  `kOverUsingTimeThreshold = 10 ms` with counter > 1; underusing if `< -threshold`; else normal.

An RTT-gradient approximation is *not* an adequate substitute: RTT from RTCP RR is a ~1 Hz,
round-trip, both-directions number; the trendline runs on per-packet one-way arrival deltas and
detects a growing queue in tens of milliseconds.

### 2.3 Loss recovery without keyframe spikes

**LTR + RPSI is not available over WebRTC.** RPSI (RFC 4585 §6.3.3) is not in `rtcp-0.17.1` at all —
the crate ships `picture_loss_indication`, `full_intra_request`, `slice_loss_indication`,
`receiver_estimated_maximum_bitrate`, `transport_layer_nack`, `transport_layer_cc` and
`rapid_resynchronization_request`, and nothing else. Chromium does not send RPSI for H.264 either;
its H.264 receive path emits NACK, PLI and FIR only. So the "receiver names a known-good reference
picture" design is closed on both ends.

**What *is* available is strictly better for our topology: we own the packetizer.** ScreenExtend
maps frames to RTP sequence numbers itself (`webrtc_session.rs:527-545`), so it can keep a
`seq → frame_index` table. Two independent signals then identify a damaged frame:

1. **NACK misses.** The webrtc-rs NACK responder keeps a `1 << 13` = 8192-packet history
   (`interceptor-0.17.1/src/nack/responder/mod.rs:41`); a NACK for a sequence number outside it is
   unrepairable. At ~1.2 KB/packet that is ~9.8 MB, ~4 s at 20 Mbps — so in practice the history
   never misses on a LAN, and this signal only fires on very deep relay stalls.
2. **TWCC "not received" status.** Once the TWCC sender interceptor is on, every feedback packet
   enumerates the per-packet delivery status. A `SymbolTypeTcc::PacketNotReceived` for a sequence
   number older than one RTT is a *definitive* loss — not a statistical `fraction_lost`. That maps,
   through our own table, to an exact damaged frame index.

That is precisely the input Sunshine's reference-frame invalidation needs:
`for (auto i = first_frame; i <= last_frame; i++) nvenc->nvEncInvalidateRefFrames(encoder, i);`
guarded by `last_frame - first_frame + 1 < ref_frames_in_dpb`, with the repaired frame tagged
`frameType = 5` (post-invalidation) rather than 2 (IDR). Moonlight signals the same thing with
`CAPABILITY_REFERENCE_FRAME_INVALIDATION_AVC`. This is already recommended as R3 in
`competitors-open-source.md`; the new contribution here is that **TWCC feedback is the WebRTC-native
way to get the frame identity**, which removes the "how would the host know?" objection.

**FEC.** The interesting and previously-unrecorded fact is in
[`media/engine/webrtc_video_engine.cc`](https://webrtc.googlesource.com/src/+/refs/heads/main/media/engine/webrtc_video_engine.cc):

```cc
if (is_decoder_factory || trials.IsEnabled("WebRTC-FlexFEC-03-Advertised"))
```

FlexFEC-03 is advertised unconditionally on the **decoder** (receive) side; only *sending* FlexFEC
is behind the `WebRTC-FlexFEC-03` field trial (*"Never enable sending FlexFEC, unless we are in the
experiment"*). ScreenExtend is the sender and Chrome is the receiver, so **a host-side FlexFEC-03
implementation would be decodable by a stock Chrome client today**, with recovery happening at the
RTP layer upstream of the packet buffer, i.e. upstream of our transform. RED+ULPFEC (RFC 2198 /
RFC 5109) is the older, more broadly supported alternative and webrtc-rs registers the
`video/ulpfec` MIME type (`webrtc-0.17.1/src/api/media_engine/mod.rs:367`) — but neither webrtc-rs
nor `interceptor-0.17.1` contains any FEC *implementation*; both would have to be written here.

Application-level Reed-Solomon the Moonlight/Sunshine way (20 % default, `MAX_FEC_BLOCKS = 4`,
`D = (255*100)/(100+F)`) is impossible inside an SRTP stream — a browser cannot be taught a custom
RTP payload. It is only reachable over a DataChannel or WebTransport video path.

Composition: NACK+RTX, FEC, and reference-frame invalidation compose cleanly and address different
regimes — NACK is cheapest when RTT is small (LAN), FEC is the only option when one RTT exceeds the
frame budget (relay), and RFI is what stops either failure from costing an IDR. Intra-refresh is
orthogonal and cheaper than all of them.

### 2.4 Codec choice — the ground moved in 2025

The `findings/speculative-webrtc-hevc-needs-a-datachannel-video-path.md` premise ("Chrome and
Safari do not offer an H.265 payload type in a WebRTC offer") **is now out of date**.

- **H.265/HEVC in WebRTC shipped in Chrome M136, enabled by default**, on desktop, Android and
  WebView ([chromestatus feature 5153479456456704](https://chromestatus.com/api/v0/features?q=H265)).
  The two flags `WebRtcAllowH265Send` and `WebRtcAllowH265Receive` gate send and receive
  separately. It is **hardware-only — there is no software fallback** — and support is queryable
  through `MediaCapabilities`. The chromestatus entry records "Safari: already shipped support".
  MDN's [WebRTC codecs guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Formats/WebRTC_codecs)
  lists H.265 as Chrome 136+ and AV1 as Chrome 113+ / Firefox 136+.
- Chromium HEVC **hardware decode** for media generally has been on by default since **Chrome 107**
  (Android 5.0+, macOS 11+, Windows 8+, ChromeOS —
  [chromestatus](https://chromestatus.com/api/v0/features?q=H.265)).
- Because the browser depacketizes H.265 before `OnAssembledFrame`, **an H.265 stream would be
  delivered to a receiver-side script transform exactly like H.264 is today** — the client change
  is a codec string (`hvc1.*`/`hev1.*`) in `transform-worker.js`'s `CODEC_CANDIDATES`, plus a
  `VideoDecoder.isConfigSupported` probe, which the worker already does
  (`transform-worker.js:141-154`).
- The host side is much cheaper than expected: **`rtp-0.17.1` already contains a working
  `HevcPayloader`** (`src/codecs/h265/mod.rs:61,198`) and webrtc-rs already defines
  `MIME_TYPE_HEVC = "video/H265"` (`api/media_engine/mod.rs:33`). What is missing is only the
  encoder wiring (NVENC HEVC GUID, VideoToolbox HEVC session, QSV HEVC) and the SDP negotiation.

**Does the win survive on LAN?** Nothing found says the *latency* changes; HEVC and AV1 buy
bitrate, not milliseconds, and on hardware encoders HEVC's per-frame encode time is comparable to
H.264 at equivalent presets. On an uncongested LAN at 20–40 Mbps the encoder is not rate-limited
and the picture is already near-transparent, so the win is ~zero. On a **congested or 2.4 GHz Wi-Fi
link, or on any relayed/cross-network session**, halving the bitrate for the same quality is
directly a latency win because it halves the airtime and the queue. That is the correct framing:
HEVC is a *congestion* feature, not a latency feature — and it should therefore be tiered on the
same locality signal as MTU and FEC.

**AV1** is the wrong call here for a different reason: hardware *decode* coverage on the client
devices that matter (phones and tablets, which is what a second-monitor product is pointed at) is
far thinner than HEVC's, and software AV1 decode at 1080p60 on a phone is a power and thermal
problem, not a latency one. HEVC hardware decode is present on essentially every iPhone/iPad since
the A9 and every Android SoC of the last decade.

**H.264 details worth fixing regardless:**

- The advertised level is `1f` = **level 3.1**, whose limit is 1280×720@30 — while the host will
  happily create a 1440p or 4K virtual display. `h264_codecs()` hardcodes `42e01f` / `4d001f` /
  `640c1f`+`64001f` (`webrtc_session.rs:74-80`). `level-asymmetry-allowed=1` is set, which lets the
  answer differ from the offer, but nothing computes a level from the actual display size. Chrome
  and WebCodecs are tolerant in practice, but a decoder that enforces DPB/MBps limits from the
  advertised level can legitimately refuse. Level 5.1 (`33`) covers 4K@60; the client's
  `CODEC_CANDIDATES` already lists `avc1.640034` (level 5.2) first, so the two sides disagree today.
- `sps-pps-idr-in-keyframe=1` is not in the fmtp (`h264_fmtp`, `webrtc_session.rs:70-72`). All three
  encoders already emit parameter sets in band on every IDR — NVENC `set_repeatSPSPPS(1)`
  (`windows_utils/streamer/nvidia/encoder.rs:620`), QSV `co2.RepeatPPS = MFX_CODINGOPTION_ON`
  (`intel/encoder.rs:445`), VideoToolbox prepends them in `sample_to_annexb_into`
  (`macos_utils/streamer/encoder.rs:414-462`) — so advertising it is honest and makes Chromium's
  depacketizer mark only true SPS+PPS+IDR frames as keyframes. Cheap correctness, no latency change.
- H.264 High profile is already offered first and is the right default: CABAC and the 8×8 transform
  are worth real bitrate on screen content, and every hardware decoder from the last decade handles
  High at these levels. MDN notes the WebRTC-mandatory baseline is Constrained Baseline and that
  `profile-level-id` must always be present (it is) and `sprop-parameter-sets` must never be (it
  isn't).

### 2.5 The network stack — what is reachable, and what it costs

**webrtc-rs sets no socket options at all.** `grep` over `webrtc-ice-0.17.1/src` and
`webrtc-util-0.17.1/src` for `SO_SNDBUF`, `IP_TOS`, `SIO_UDP_CONNRESET`, `socket2`,
`set_send_buffer` returns nothing. ICE sockets come from `listen_udp_in_port_range` with OS
defaults. `RECEIVE_MTU` is 1460 (`webrtc-0.17.1/src/lib.rs:46`) and is only the read buffer size.

**The one hook that exists is `UDPMux`, and it has a real cost.**
`SettingEngine::set_udp_network(UDPNetwork::Muxed(mux))`
(`webrtc-0.17.1/src/api/setting_engine/mod.rs:168-173`) takes an
`Arc<dyn UDPMux>`; `UDPMuxDefault::new(UDPMuxParams::new(conn))` accepts **any** `C: Conn`
(`webrtc-ice-0.17.1/src/udp_mux/mod.rs:51-64`), and `impl Conn for tokio::net::UdpSocket` exists
(`webrtc-util-0.17.1/src/conn/conn_udp.rs:6`). So a `socket2::Socket` configured however we like,
converted to a `tokio::net::UdpSocket`, can become the ICE transport — one fixed port, per-local-IP
host candidates (`agent_gather.rs:385-470`).

**But:** `webrtc-ice-0.17.1/src/agent/agent_gather.rs:117-120`

```rust
CandidateType::ServerReflexive => {
    let ephemeral_config = match &params.udp_network {
        UDPNetwork::Ephemeral(e) => e,
        // No server reflexive for muxxed connections
        UDPNetwork::Muxed(_) => continue,
    };
```

**Muxed mode silently disables server-reflexive (STUN) candidate gathering.** Relay/TURN gathering
is unaffected (`agent_gather.rs:156-166` uses its own sockets). pion has `UniversalUDPMux` for
exactly this; webrtc-rs 0.17.1 has no equivalent (`grep -ri universal` over `webrtc-ice-0.17.1/src`
returns nothing). So socket-level tuning and NAT-traversal-by-STUN are mutually exclusive today,
which makes this a **LAN-tier-only** change unless the mux is patched upstream.

**Windows DSCP.** Raw `setsockopt(IP_TOS)` is not the mechanism on Windows; the supported API is
qWAVE. [`QOSCreateHandle`](https://learn.microsoft.com/en-us/windows/win32/api/qos2/nf-qos2-qosaddsockettoflow)
then `QOSAddSocketToFlow(h, socket, dest, TrafficType, QOS_NON_ADAPTIVE_FLOW, &flowId)` on the
socket handle. The [`QOS_TRAFFIC_TYPE`](https://learn.microsoft.com/en-us/windows/win32/api/qos2/ne-qos2-qos_traffic_type)
mapping is documented exactly:

| Traffic type | DSCP | 802.1p |
| --- | --- | --- |
| `QOSTrafficTypeBestEffort` (0) | none (no marking at all) | none |
| `QOSTrafficTypeBackground` (1) | 0x08 | 2 |
| `QOSTrafficTypeExcellentEffort` (2) | 0x28 | 5 |
| `QOSTrafficTypeAudioVideo` (3) | **0x28** (CS5) | **5** |
| `QOSTrafficTypeVoice` (4) | 0x38 | 7 |
| `QOSTrafficTypeControl` (5) | 0x38 | 7 |

802.1p tags are only added when the flow is *adaptive* (no `QOS_NON_ADAPTIVE_FLOW`), the destination
is on the local link, and qWAVE has determined the tags are not being discarded — which is exactly
the LAN second-monitor case, so it is worth *not* passing the non-adaptive flag on a same-subnet
session. Setting an arbitrary DSCP via
[`QOSSetFlow(..., QOSSetOutgoingDSCPValue, ...)`](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/api/qos2/nf-qos2-qossetflow)
**requires Administrators or Network Configuration Operators membership** — the traffic-type route
does not, which is why it is the one to use. `QOSAddSocketToFlow` needs the `DestAddr` if the socket
is unconnected, which ours is (ICE uses `send_to`); the address is known once the candidate pair is
nominated.

DSCP 0x28 = CS5 is what maps to **WMM AC_VI** on Wi-Fi, which is the whole point: AC_VI has a
shorter contention window and a longer TXOP than AC_BE, so on a busy AP the video gets to the air
sooner. Marking input as `QOSTrafficTypeControl`/`Voice` (AC_VO) would be right in principle, but
input and video share one UDP socket under BUNDLE, so a single flow must be chosen — AC_VI for
everything is the correct compromise.

**macOS DSCP / WMM.** `SO_NET_SERVICE_TYPE = 0x1116` on a socket, with values from
[`xnu bsd/sys/socket.h`](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/socket.h):
`NET_SERVICE_TYPE_BE 0`, `BK 1`, `SIG 2`, `VI 3` (Interactive Video), `VO 4` (Interactive Voice),
`RV 5` (Responsive Multimedia A/V), `AV 6` (Multimedia A/V Streaming), `OAM 7`, `RD 8`. The header
is explicit that these are *"not priorities but rather different categories of delay, jitter and
loss parameters"*, that they may drive *"layer 2 packet marking with the appropriate WMM Access
Category"*, and cites RFC 4594. `NET_SERVICE_TYPE_RV` is the closest match for interactive
screen streaming; `VI` is the safe choice. This is a one-line `setsockopt` and needs no
entitlement — but, like Windows, it needs the socket, i.e. the UDPMux.

**Other socket knobs, ranked:**

- `SO_SNDBUF` ~1 MB. Sunshine sets `send_buffer_size(1024*1024)` explicitly. With a default buffer
  a 200 KB IDR burst can hit `WSAEWOULDBLOCK`/`EWOULDBLOCK` and be dropped inside our own process.
  Worth doing *with* the pacer, not instead of it.
- `SIO_UDP_CONNRESET = FALSE` on Windows. An unconnected UDP socket that receives an ICMP
  port-unreachable makes the *next* `recv_from` fail with `WSAECONNRESET`; nothing in webrtc-rs
  disables this, and nothing in ScreenExtend does either. This is the classic Windows UDP server
  footgun and the standard fix is one `WSAIoctl`.
- `IP_DONTFRAGMENT` / `IP_MTU_DISCOVER`: relevant only in combination with the relayed-path MTU
  reduction already filed (`findings/major-webrtc-rtp-mtu-fixed-at-1188-on-relayed-paths.md`).
- GSO (`UDP_SEGMENT` on Linux, USO on Windows): batches N datagrams into one syscall. It is the
  *opposite* of pacing — it exists to make bursts cheaper, not smoother — and webrtc-rs sends one
  `send_to` per packet anyway. Skip.
- Nagle: irrelevant for UDP; the HTTP/WHEP side already sets `TCP_NODELAY` via
  `axum_server::accept::NoDelayAcceptor` (`server.rs:311-320`).

**Wi-Fi, radio side.** 5 GHz or 6 GHz over 2.4 GHz is the single biggest environmental lever, and
`detect_session_locality` already emits the right warning about AP client isolation forcing a
same-subnet pair through the router (`webrtc_session.rs:246-253`). On the client, 802.11
power-save is the risk: a phone in PS mode only wakes at DTIM beacons, adding tens of milliseconds
of downlink latency. WMM U-APSD lets the station trigger a delivery burst by sending an *uplink*
frame in the same access category — which ScreenExtend gets for free, because the input DataChannel
and the client's RTCP both send uplink packets continuously; the existing 1 s input ping
(`static/input.js:507`) is a crude version of the same thing. A screen wake lock (`nosleep.js`)
keeps the display on but does **not** by itself keep the radio out of power save. Multicast and
broadcast are to be avoided entirely on Wi-Fi (they are sent at the basic rate and are not
acknowledged); ScreenExtend uses none, though `webrtc-mdns` is in the tree — mDNS ICE candidates
would be a broadcast dependency, and `SettingEngine::set_ice_multicast_dns_mode` is not called, so
the default applies. Worth checking which default that is.

### 2.6 WebTransport over HTTP/3 — the plumbing is ready, the evidence is not

**Support finally exists everywhere.** WebTransport reached Baseline "newly available" in **March
2026** when Safari shipped it; caniuse puts global support at **91.3 %**
([MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport),
[caniuse](https://caniuse.com/webtransport)).

| | Chrome/Edge | Firefox | Safari macOS + iOS |
| --- | --- | --- | --- |
| `WebTransport` | 97 / 98 | 114 | **26.4** ([WebKit blog, 24 Mar 2026](https://webkit.org/blog/17862/webkit-features-for-safari-26-4/)) |
| `datagrams`, `maxDatagramSize`, `incoming/outgoingMaxAge` | 97 | 114 | 26.4 |
| **`serverCertificateHashes`** | **100** | **125** | **26.4** |
| `sendOrder` / `createSendGroup()` (stream priority) | **not shipped** ([chromestatus 5183354944225280](https://chromestatus.com/api/v0/features/5183354944225280), *Proposed*) | 119 / 155 | 26.4 |
| session `getStats()` | **not shipped** ([crbug 41492543](https://crbug.com/41492543)) | 114, *throws not-implemented* | 26.4 |
| `congestionControl` hint, `requireUnreliable`, `reliability` | not supported | 114 | 26.4 |
| Subject to Local Network Access | **147** | — | — |

Source: [MDN browser-compat-data `api/WebTransport.json`](https://raw.githubusercontent.com/mdn/browser-compat-data/main/api/WebTransport.json).
There is no browser with WebTransport but without datagrams. The spec is
[draft-ietf-webtrans-http3-16](https://datatracker.ietf.org/doc/draft-ietf-webtrans-http3/)
(6 Jul 2026) — **in WG Last Call, not an RFC**.

**Datagrams vs streams.** RFC 9221 §5.4 is explicit that datagrams *are* congestion controlled:
*"DATAGRAM frames employ the QUIC connection's congestion controller… The sender MUST either delay
sending the frame until the controller allows it or drop the frame without sending it"*
([RFC 9221](https://www.rfc-editor.org/rfc/rfc9221.html)). They are ack-eliciting but never
retransmitted, and there is **no transport-level fragmentation** — a 200 KB keyframe is ~170
datagrams you must number, reassemble and time out yourself, i.e. reimplementing RTP. At 14
fragments per frame and 1 % independent loss, 13 % of frames are damaged; at 5 %, 51 %.
`maxDatagramSize` is implementation-defined and not published; plan for ~1150–1250 usable bytes
(QUICHE `kDefaultMaxPacketSize = 1250`, quinn `min_mtu = 1200`).

**The industry answer is streams, not datagrams.** MoQ
([draft-ietf-moq-transport-20](https://www.ietf.org/archive/id/draft-ietf-moq-transport-20.html),
31 Aug 2026, still an I-D) sends a subgroup *"on a single stream whenever possible"* and reserves
datagrams for an explicit per-object forwarding preference, *"because many QUIC and WebTransport
implementations offer the ability to control the relative scheduling priority of pending stream
data"*. One unidirectional stream per frame gives retransmission *within* a frame and independence
*between* frames — strictly better than TCP and better than bare datagrams. Streams are created
implicitly by their first STREAM frame, so there is no per-frame handshake; the costs are
stream-credit bookkeeping (3600 stream IDs/minute at 60 fps) and having to `RESET_STREAM` a
superseded frame instead of getting `outgoingMaxAge` for free.

**Certificates line up with `tls.rs` unusually well.** `serverCertificateHashes` requires an X.509v3
cert, **validity < 2 weeks**, **SHA-256 only**, and an allowed key algorithm — the spec says
*"minimally must include ECDSA with secp256r1 (NIST P-256)"* and *"must NOT include RSA keys"*
([MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebTransport/WebTransport)). Chromium
enforces the window literally —
`constexpr int kCustomCertificateMaxValidityDays = 14;`
([`net/quic/dedicated_web_transport_http3_client.cc`](https://raw.githubusercontent.com/chromium/chromium/main/net/quic/dedicated_web_transport_http3_client.cc)) —
and QUICHE's verifier currently accepts P-256/P-384/Ed25519 and, with a `TODO` against it, RSA
([`web_transport_fingerprint_proof_verifier.cc`](https://raw.githubusercontent.com/google/quiche/main/quiche/quic/core/crypto/web_transport_fingerprint_proof_verifier.cc)).
It forces a dedicated connection (no pooling) and works **only over HTTP/3**.

ScreenExtend already generates a self-signed cert at runtime with `rcgen` and caches it
(`streamer/tls.rs`). `rcgen` 0.14.10 (28 Aug 2026) exposes `PKCS_ECDSA_P256_SHA256` and
`not_before`/`not_after`, and `wtransport`'s `Identity::self_signed()` already implements the whole
rule and quotes the constraints in its docs. A **secure context is required** and the URL scheme
must be `https` — and a self-signed HTTPS origin *does* qualify, because
[Secure Contexts §3.1](https://w3c.github.io/webappsec-secure-contexts/) is scheme-based and says
nothing about certificate validation. So this tier exists only on port 8443, never on the plain-HTTP
8080 path. The work: a **second** ECDSA P-256 cert with ≤13-day validity, rotated on start and on a
timer (publishing old+new hashes in the array so rotation does not break live sessions), and its
SHA-256 substituted into `index.html` exactly the way `__SAME_DEVICE_FLAG__` already is.

**Rust server:** `wtransport` 0.7.2 (11 Aug 2026, MIT/Apache-2.0, on quinn ^0.11.6) is the only
crate that gives HTTP/3 + datagrams + `max_datagram_size` + per-stream `set_priority` + a
spec-compliant self-signed identity in one dependency — but its README says it is *"not considered
completely production-ready"*. `web-transport-quinn` 0.12.1 is MoQ's own and more downloaded but
documents neither hash-pinning helpers nor priority. `h3-webtransport` 0.1.2 has not been released
since May 2025 and its parent is *"still very experimental"*. `s2n-quic` has no WebTransport layer.
Dependency impact is better than feared: `webrtc 0.17.1` uses `ring ^0.17.14` and **no rustls**
(it has its own `dtls` crate), so quinn's rustls 0.23 is additive and the only duplicate is
`rcgen` 0.13 alongside 0.14. **quinn 0.11.11** offers GSO (`enable_segmentation_offload`, Linux/
Windows; degrades on macOS), NewReno/Cubic/BBR — with BBR marked *"Experimental! Use at your own
risk."* — and **no exposed pacing control**.

**The latency evidence does not exist.** The only direct comparison found is
[arXiv:2505.22132](https://arxiv.org/abs/2505.22132) (May 2025), MoQ/RoQ vs WebRTC for holographic
conferencing over Wi-Fi and 5G: *"approximately 30 % in latency"* and *"approximately 60 %"* faster
startup — with **no absolute milliseconds, no glass-to-glass measurement and no LAN condition**, and
framed as expected rather than measured. Cloudflare's MoQ relay post
([blog.cloudflare.com/moq](https://blog.cloudflare.com/moq/), 330+ cities) and moq-rs publish
adjectives, not numbers. **No WebTransport-vs-WebRTC LAN benchmark exists.**

The counter-evidence is stronger and directly relevant, because our receivers are phones:
[*QUIC is not Quick Enough over Fast Internet*, WWW '24](https://arxiv.org/abs/2310.09423) measured
*"a data rate reduction of up to 45.2 % compared to the TCP+TLS+HTTP/2 counterpart"*, growing with
bandwidth, root-caused to *"high receiver-side processing overhead, in particular, excessive data
packets and QUIC's user-space ACKs"*. GSO helps the sender and does nothing for the browser. And
[draft-ietf-quic-ack-frequency](https://datatracker.ietf.org/doc/draft-ietf-quic-ack-frequency/)
has **expired** at -14, with no browser-side API, so the ACK rate is not negotiable.

Also: **no WHIP/WHEP-over-WebTransport spec exists.** WISH has RFC 9725 (WHIP) and
`draft-ietf-wish-whep-04`, and nothing else
([WISH documents](https://datatracker.ietf.org/wg/wish/documents/)). Every framing decision —
fragmentation, keyframe request, reconfig, kick, audio, the OTP/device-token join — would be new
code duplicating `webrtc_session.rs`, `server.rs` and `session.rs`, and a third transport threaded
through `AppState`, `serve` and the CLI.

**WebSocket over TCP as a floor.** Modelling a 20 ms RTT path with 1400-byte segments: 8 Mbps
1080p60 is ~12 packets/frame, 20 Mbps is ~30. P(frame contains a loss) is 11.4 % / 26.0 % at 1 %
loss and 46.0 % / 78.5 % at 5 %. The cost of each hit: fast retransmit ≈ 1–1.5 RTT (20–30 ms,
1–2 frames); a **tail** loss falls to RACK-TLP, whose *"default PTO interval is 2\*SRTT"*
([RFC 8985](https://www.rfc-editor.org/rfc/rfc8985.html)) → 40 ms + ½ RTT ≈ **3 frames**; and an RTO
is 200 ms on Linux (`#define TCP_RTO_MIN ((unsigned)(HZ / 5))`,
[include/net/tcp.h](https://raw.githubusercontent.com/torvalds/linux/master/include/net/tcp.h)) or
the RFC 6298 1 s floor — **12 to 60 frames**. Worse, TCP's in-order delivery withholds frames that
have *already arrived*, so surviving an RTO needs ~200 ms of buffer, which is larger than the entire
latency budget. Linux `TCP_DELACK_MIN` = 40 ms slows dupack generation and pushes losses toward the
TLP case. Notably, both projects that ship *both* transports default to WebSocket:
[Selkies](https://raw.githubusercontent.com/selkies-project/selkies/main/README.md) *"streams over
plain WebSockets by default, with WebRTC available as an opt-in transport"* and
[KasmVNC](https://raw.githubusercontent.com/kasmtech/KasmVNC/master/README.md) pairs WebSocket with
WebCodecs H.264/H.265/AV1 — for deployment simplicity, not latency; neither publishes numbers.
WebSocket is a legitimate *compatibility floor*, never a latency tier.

**Raw UDP from a browser is impossible, confirmed.** The Direct Sockets API is Isolated-Web-App-only
*by design*: *"The API is planned to be available only in Isolated Web Apps which themselves provide
a decent level of security thanks to a transparent update model and strict Content Security Policy"*
([WICG explainer](https://raw.githubusercontent.com/WICG/direct-sockets/main/docs/explainer.md)).
Every Direct Sockets entry on chromestatus is annotated "Isolated Web Apps only", including the
Chrome 144 multicast and Chrome 151 permission-policy work; normal pages and installed PWAs cannot
use it. Mozilla's standards position is **negative**
([standards-positions#431](https://github.com/mozilla/standards-positions/issues/431)). There is no
"WebSocket over UDP". `RTCDataChannel` (SCTP/DTLS/UDP) and WebTransport (QUIC/UDP) remain the only
UDP-backed byte pipes a web page gets.

### 2.7 Input

The client already does the right thing. `RemoteInput.setup` (`static/input.js:490-495`) opens
three channels:

```js
fast     = pc.createDataChannel('fast',     { ordered: false, maxRetransmits: 0, priority: 'high' });
reliable = pc.createDataChannel('reliable', { ordered: true,  priority: 'high' });
bulk     = pc.createDataChannel('bulk',     { ordered: true });
```

with `channelFor(op)` routing pointer moves/batches/wheel/zoom/enter-leave to `fast`, keys and
lifecycle to `reliable`, and clipboard/drag/drop to `bulk` (`input.js:57-82`), plus a
`bufferedAmount > 8192` drop guard on `fast`. That matches or beats every comparable — Input
Leap's whole trick is `TCP_NODELAY`, which an unordered SCTP channel already dominates.

**Does a video burst delay a DataChannel message?** Two different answers per direction.

- *Host → client* (audio DataChannel, BYE): SRTP and SCTP-over-DTLS share one ICE conn and one UDP
  socket under BUNDLE. In webrtc-rs there is no shared userspace queue — `SrtpWriterFuture` and the
  DTLS/SCTP path each call `Conn::send` directly — so the contention is purely at the OS socket and
  the NIC/radio. A 170-packet unpaced video burst therefore *does* sit in front of an audio
  DataChannel packet in the kernel queue and on the air. This is a second, independent argument for
  the pacer.
- *Client → host* (input): this is Chromium's usrsctp. One association, one congestion window
  shared by `fast`, `reliable` and `bulk`, so a large `bulk` clipboard/file transfer can genuinely
  delay a pointer move. `priority: 'high'` maps to the SCTP stream scheduler's priority, which
  helps but does not partition the cwnd.
- For the host's own outbound SCTP, webrtc-rs's `PendingQueue` keeps **separate unordered and
  ordered queues and drains the unordered one first** (`webrtc-sctp-0.17.1/src/queue/pending_queue.rs`,
  `peek()`), with a 128 KiB byte limit enforced by an async semaphore in `push()` — so a large
  ordered send applies backpressure to the sender but does not get in front of unordered traffic.

## 5. Recommendations

Ranked by expected latency delta ÷ implementation cost. Each is one `findings/` file.

### R1 — Parse REMB and stamp `abs-send-time`. *(hours; the cheapest real BWE in the repo)*

**API.** Add `HeaderExtension::AbsSendTime(...)` to the array already passed to
`track.write_rtp_with_extensions` (`webrtc_session.rs:505-539`) and register the
`http://www.webrtc.org/experiments/rtp-hdrext/abs-send-time` extension next to playout-delay
(`webrtc_session.rs:164-172`). Add one `downcast_ref::<ReceiverEstimatedMaximumBitrate>()` arm to
the RTCP loop at `webrtc_session.rs:472-483` and feed `remb.bitrate` into `BitrateController`.

**Why it works.** Chromium chooses receive-side BWE per packet when no transport sequence number is
present, and picks `RemoteBitrateEstimatorAbsSendTime` when `abs-send-time` *is*
([receive_side_congestion_controller.cc](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/receive_side_congestion_controller.cc)).
`goog-remb` is already advertised, so REMB is very likely already arriving and being thrown away.
This gets Google's own arrival-time filter running *in the browser*, for free.

**Platform.** All. **Probe:** if no REMB arrives within 5 s, log it and keep the loss path.
**Expected win.** Replaces a ~1 Hz loss-only signal with a delay-based estimate that is pushed
immediately on any decrease (`RembThrottler`, 200 ms throttle for increases). This is the single
biggest correctness improvement available for a day's work.
**Measure.** Log every REMB against the current target during a `clumsy`/`tc netem` bandwidth
step-down; time-to-first-cut, and standing RTT.

### R2 — Pace the per-frame RTP burst. *(already filed; this report adds the numbers)*

**API.** Token bucket / group-spread in the writer loop (`webrtc_session.rs:527-545`), rate
`2.5 × target`, group size 8, budget `min(0.6 × frame_interval, 8 ms)`, hard flush at the frame
deadline. **Platform.** All. **Probe.** None; consider skipping it for
`SessionLocality::SameNetwork` on a wired link once measured.
**Expected win.** Removes the 167 Mbps-equivalent microburst; on a busy AP this is where the p99
tail and most induced loss live. **Measure.** `totalAssemblyTime / framesAssembledFromMultiplePackets`
on the client (available only on the `<video>` path — so measure there, or via a Wireshark RTP
inter-arrival plot on the fast path), plus `fraction_lost` and PLI/min.

### R3 — Prefer `RTCRtpScriptTransform` on Chrome 141+. *(one line; already filed, now with versions)*

`const useScriptTransform = hasScriptTransform;` (`static/index.html:169`). MDN BCD gives
`RTCRtpReceiver.transform` and `sendKeyFrameRequest` at **Chrome 141**, Firefox 117, Safari 15.4;
`createEncodedStreams` is Chrome-only and has no keyframe request. Keep the legacy branch for
Chrome < 141. This is the difference between a 250 ms recovery and a 4 s freeze followed by
demotion to `<video>`.

### R4 — Delete the two dead latency levers on the fast path, and document why.

`playoutDelayHint = 0` (`index.html:832`) and `jitterBufferTarget = 0` (`index.html:874`) do
nothing on the WebCodecs path because the frames never reach `FrameBuffer` (§2.1). Leaving them is
harmless but actively misleading — it is why Selkies' warning about pinning them to zero was
considered and dismissed as "probably correct here" without a mechanism. Keep them *only* on the
`<video>` fallback (`index.html:922-923`), where they are real, and A/B `0` vs `10–30 ms` there.
Likewise `PlayoutDelayExtension::new(0, 0)` (`webrtc_session.rs:505-507`) is inert for any client
on the fast path and only matters for fallback clients — which is exactly the case where the
locality-dependent `(0, 200)` proposal in
`findings/minor-webrtc-playout-delay-zero-is-chromium-only-and-unconditional.md` applies.

### R5 — Send-side TWCC + a trendline estimator + NACK/TWCC-driven reference-frame invalidation.

**API.** Replace `register_default_interceptors` with `configure_nack` + `configure_rtcp_reports` +
a **custom** TWCC sender interceptor (copy `interceptor-0.17.1/src/twcc/sender/`, ~60 lines, adding
a `(seq, Instant)` ring). Parse `TransportLayerCc` in the existing RTCP loop
(`recv_deltas` are already in microseconds; `reference_time` is in 64 ms units). Run the trendline
from §2.2 with libwebrtc's constants. Then join TWCC's per-packet `PacketNotReceived` against our
own `seq → frame_index` table to drive `nvEncInvalidateRefFrames` (Sunshine's exact call) instead
of a full IDR.
**Platform.** BWE all; RFI NVENC first (QSV/VideoToolbox have no equivalent, so intra-refresh
covers them). **Probe.** If the answer omits the TWCC extmap, fall back to R1's REMB path.
**Expected win.** Cuts before the queue fills rather than after 10 % loss; and turns every
recoverable loss from an IDR-sized burst into a normal P-frame. **Measure.** Standing RTT during a
bandwidth step-down; IDRs per minute; encoded size of the frame following each loss event.

### R6 — HEVC as a probed tier, gated on locality.

**API.** Register `MIME_TYPE_HEVC` in the media engine, use the existing
`rtp-0.17.1::codecs::h265::HevcPayloader`, add HEVC GUIDs to the NVENC/VideoToolbox/QSV backends,
add `hvc1.*`/`hev1.*` to `transform-worker.js:24-32`.
**Platform/version.** Chrome ≥ 136 (default-on, desktop/Android/WebView, **hardware decode only,
no software fallback**), Safari (already shipped). **Probe at runtime, never by version:** the
client already runs `VideoDecoder.isConfigSupported` over its candidate list
(`transform-worker.js:141-154`) and reports `audioCapabilities` in the WHEP body
(`index.html:967`) — add a `videoCapabilities` field the same way, and offer H.265 in the answer
only when the client reported it *and* the offer contains an H.265 payload type.
**Expected win.** ~0 ms on an idle LAN. 30–50 % less bitrate for the same picture, which is
directly a latency win on a congested AP and on every relayed session. **Gate it on
`SessionLocality`** for the same reason MTU and FEC should be. **Measure.** Same quality target,
compare `fraction_lost` and p99 display lag at a fixed offered bitrate on a loaded 2.4 GHz AP.

### R7 — Own the UDP socket (LAN tier only): DSCP/qWAVE, `SO_SNDBUF`, `SIO_UDP_CONNRESET`.

**API.** `socket2::Socket` → configure → `tokio::net::UdpSocket` →
`UDPMuxDefault::new(UDPMuxParams::new(sock))` → `SettingEngine::set_udp_network(UDPNetwork::Muxed(..))`.
Then per platform: Windows `QOSCreateHandle` + `QOSAddSocketToFlow(..., QOSTrafficTypeAudioVideo,
...)` (DSCP 0x28 / 802.1p 5 / WMM AC_VI, **no admin needed** — unlike `QOSSetOutgoingDSCPValue`);
macOS `setsockopt(SOL_SOCKET, SO_NET_SERVICE_TYPE /*0x1116*/, NET_SERVICE_TYPE_VI /*3*/)`.
Plus `SO_SNDBUF` 1 MB and `SIO_UDP_CONNRESET=false` on Windows.
**Cost — read this before implementing.** `UDPNetwork::Muxed` **disables server-reflexive candidate
gathering** in webrtc-rs 0.17.1 (`agent_gather.rs:117-120`). TURN relay still works. So this must be
selected per session or per host mode: muxed for LAN-only hosting, ephemeral whenever cloud/STUN is
enabled — or upstream a `UniversalUDPMux` to webrtc-rs.
**Probe.** `QOSCreateHandle` failing (qWAVE service off) or `setsockopt` returning `ENOPROTOOPT` →
carry on unmarked. **Measure.** Two clients on one AP, one running iperf: p99 display lag with and
without the marking. On a WMM-capable AP expect a clear separation; on a consumer AP that ignores
DSCP, expect none — which is itself the answer.

### R8 — FlexFEC-03 for relayed sessions only.

**API.** Write a FlexFEC-03 sender (XOR masks, separate SSRC and payload type) — neither webrtc-rs
nor `interceptor-0.17.1` has one. **Why it is now worth considering:** Chromium advertises
FlexFEC-03 on the **decoder** side unconditionally (`is_decoder_factory || trials.IsEnabled(...)`),
so a stock Chrome client can already receive it; only *sending* it from Chrome is gated. Recovery
happens upstream of the packet buffer, hence upstream of our transform.
**Gate on `SessionLocality::CrossNetwork`** — on a 1–3 ms LAN, NACK is strictly cheaper than 20 %
parity. Lowest priority, highest cost of anything here.

### R9 — Advertise a truthful H.264 level, and `sps-pps-idr-in-keyframe=1`.

`h264_codecs()` (`webrtc_session.rs:74-80`) hardcodes level 3.1 (`…1f`) for every resolution while
the client asks for level 5.2 (`avc1.640034`) first. Compute the level from the negotiated display
size and put it in both the fmtp and the `codechint` message. Add `sps-pps-idr-in-keyframe=1` to
`h264_fmtp` — all three encoders already satisfy it. No latency change; removes a class of
"why won't this decode on device X".

### R10 — WebTransport as a probed tier: **not yet**, and here is the exact bar it must clear.

**Verdict: defer.** The plumbing is ready and fits this codebase unusually well — Chrome 97+,
Firefox 114+, **Safari 26.4+ on macOS and iOS**, `serverCertificateHashes` in all three, an
`rcgen`-based self-signed cert story that maps onto the ≤14-day ECDSA P-256 rule almost exactly, no
`ring`/rustls collision with webrtc-rs, and `wtransport 0.7.2` giving HTTP/3 + datagrams + per-stream
priority + a spec-compliant self-signed identity in one dependency. What is missing is any reason to
believe it is faster *here*:

1. **No LAN benchmark exists anywhere** — the single WebTransport-vs-WebRTC comparison found
   (arXiv:2505.22132) reports ~30 % latency / ~60 % startup on Wi-Fi and 5G with no absolute
   milliseconds and no LAN condition. On a 1 ms LAN, SRTP is already at the floor.
2. **Chrome has not shipped `sendOrder`/`sendGroup`** — the stream prioritization that makes the
   one-stream-per-frame design work is a no-op on the largest client population.
3. **Chrome has no session `getStats()`** and Firefox's throws, so the `getStats`-driven bitrate
   loop would have to be rebuilt in-band.
4. **QUIC costs the receiver CPU** — up to 45.2 % throughput reduction vs TCP+TLS, root-caused to
   user-space ACK processing, on devices that are phones.
5. **Two nested congestion controllers.** RFC 9221 §5.4 means QUIC will delay or drop our datagrams
   underneath our own bitrate driver, with quinn offering loss-based Cubic (standing queue) or a BBR
   it labels experimental, and no pacing control.
6. **No WHEP-over-WebTransport spec**, so the whole signaling/reconfig/kick/audio/OTP surface is
   bespoke new code and a third transport through `AppState`/`serve`/CLI.

**The bar for revisiting:** Chrome ships `sendOrder` (track
[chromestatus 5183354944225280](https://chromestatus.com/api/v0/features/5183354944225280)) **and**
someone publishes — or we measure — a LAN glass-to-glass comparison that beats the post-R1/R2/R5
WebRTC path. If it is built anyway, build it as **one unidirectional stream per frame** with
server-side `SendStream::set_priority` (not datagrams, and not relying on browser `sendOrder`), on
a second ECDSA P-256 identity with 13-day validity rotated on start plus a timer, hash substituted
into `index.html` the way `__SAME_DEVICE_FLAG__` already is, HTTPS-only, with WHEP kept as the
default and the fallback.

**WebSocket** is worth having as a *compatibility floor* for clients with no WebRTC at all — but
never as a latency tier: at 20 ms RTT a tail loss costs ~3 frames via RACK-TLP and an RTO costs
12–60, and TCP's in-order delivery withholds frames that already arrived.

### Recommendations that were investigated and rejected

- **LTR + RPSI.** RPSI is absent from `rtcp-0.17.1` and Chromium does not send it for H.264. Closed
  on both ends. Use NACK/TWCC-driven RFI (R5) instead.
- **Application-level Reed-Solomon (Moonlight-style).** Impossible inside SRTP — a browser cannot
  be taught a custom RTP payload format. Only reachable on a DataChannel/WebTransport video path.
- **AV1.** Client hardware decode coverage on phones and tablets is much thinner than HEVC's, and
  software AV1 at 1080p60 on a phone is a thermal problem. Revisit when SoC coverage is universal.
- **GSO / `UDP_SEGMENT`.** It optimises bursts, which is the thing we are trying to remove.
- **`enable_sender_rtx(true)`.** Already filed as speculative; `ResponderInternal::resend_packets`
  looks the stream up by `nack.media_ssrc`, so the flag alone probably does not route repairs onto
  the RTX SSRC. Verify with a capture before touching it.

## 6. Verification plan

**Prerequisite (blocks everything).** `findings/major-client-no-glass-to-glass-telemetry.md` — the
client's `videoDelayEmaMs` subtracts a Unix-epoch wall clock from a monotonic host epoch, so it is
not a latency. Every "measure display lag before/after" below is void until that lands.

1. **Confirm §2.1 empirically.** Join from Chrome with the WebCodecs path active, open
   `chrome://webrtc-internals`, and record which `inbound-rtp` counters are zero. Expect
   `framesDecoded`, `framesReceived`, `jitterBufferDelay`, `totalProcessingDelay`,
   `totalAssemblyTime`, `framesAssembledFromMultiplePackets`, `pliCount` at zero and
   `bytesReceived`/`packetsReceived`/`packetsLost`/`nackCount` live. Then repeat on the `<video>`
   fallback and confirm they populate. This single experiment validates R2's measurement plan and
   R4 at once.
2. **Confirm REMB is arriving (R1).** Before any code change, add a temporary
   `tprintln!("{:?}", p)` for every RTCP packet type in the loop at `webrtc_session.rs:472-483` and
   count `ReceiverEstimatedMaximumBitrate` packets per minute from a Chrome client. If they are
   there, R1 is a few hours' work with a guaranteed payoff. If they are not, find out why before
   building anything on it.
3. **Pacing (R2).** Wireshark on the client, RTP inter-packet arrival deltas. Before: a dense
   cluster then a frame-interval gap. After: sub-bursts spread across the frame period, the Stadia
   shape. Three link conditions: wired, clean 5 GHz, 5 GHz with a competing 4 K stream. Wired must
   not regress; the loaded case is where the win is.
4. **BWE (R1/R5).** `clumsy` (Windows) step-down from 40 to 8 Mbps. Record time-to-first-cut,
   overshoot, and standing RTT. Today's controller has a 2–10 % loss dead band, so expect it to
   ride through the step until loss exceeds 10 %.
5. **Loss recovery (R5).** Inject 2 % / 5 % loss. Count `RTCP PLI received` lines
   (`webrtc_session.rs:476`) per minute and the encoded size of the frame that follows each.
6. **Codec (R6).** Fixed offered bitrate, same scene, H.264 High vs HEVC: `fraction_lost` and p99
   display lag on a loaded AP; and encode time per frame on the host.
7. **DSCP (R7).** Two stations on one AP, one saturating with iperf. p99 display lag marked vs
   unmarked. Verify the marking actually reaches the air with a monitor-mode capture if one is
   available — many consumer APs ignore DSCP entirely and that is the expected null result.

**Cannot be verified on the dev boxes.** macOS 10.15.8 Intel with Command Line Tools only: no SCK,
no VideoToolbox low-latency, no HEVC encode testing worth the name, and no way to test
`SO_NET_SERVICE_TYPE` against a modern AP. AMD is a stub. A genuinely cross-network relayed session
needs a second network, not a loopback TURN — so R8 and the relayed half of R6/R7 are unverifiable
locally. Safari `RTCRtpScriptTransform` behaviour needs a real iOS device.

## 7. Open questions

1. Does Chrome actually emit REMB for this session shape? Everything in §2.2 says yes, but it is a
   ten-minute experiment (verification step 2) and R1's entire value rests on it.
2. Does the frame transformer delegate's thread hop (`TransformFrame` posts to the transform's task
   queue and the worker reads it) cost anything measurable versus the in-process frame buffer path?
   Sub-millisecond by inspection, but unmeasured.
3. `UDPMux` disabling srflx is a webrtc-rs limitation, not a protocol one — pion has
   `UniversalUDPMux`. Is upstreaming it cheaper than maintaining two socket modes?
4. Does Chrome's H.265 receive path actually deliver H.265 frames to a receiver-side script
   transform? The architecture says yes (depacketization is upstream of `OnAssembledFrame`), but it
   has not been observed and there is no reason to build R6 before someone tries it with a
   hand-rolled H.265 offer.
5. Does turning on send-side TWCC change Chrome's own receive behaviour in a way we do not want —
   specifically, does it stop sending REMB (yes, by §2.2's per-packet branch), and is the trendline
   we would write better than the `RemoteBitrateEstimatorAbsSendTime` we would lose? R1 before R5
   for that reason.
6. What is `SettingEngine`'s default `ice_multicast_dns_mode`, and does ScreenExtend emit mDNS ICE
   candidates? On Wi-Fi that is broadcast traffic at the basic rate, and it would show up as
   gathering latency.
7. Is there any published WebTransport-vs-WebRTC glass-to-glass measurement on a LAN? Nothing found.
   If ScreenExtend ever measures one, it would be the first — which is itself a reason to be
   suspicious that the gain is small enough that nobody bothered to publish it.
8. Does Chrome's Local Network Access gate (applied to WebTransport from Chrome 147) fire for a page
   served *from* the LAN host it then dials? Almost certainly not — the page is already in the local
   address space — but it is exactly the kind of thing that breaks a LAN product in a Chrome update,
   and it would matter for a cloud-hosted join page.
9. Selkies warns against pinning `jitterBufferTarget`/`playoutDelayHint` to zero. §2.1 says that
   warning cannot apply to the WebCodecs path (the levers are inert there) and *does* apply to the
   `<video>` fallback — which is exactly where the code sets them to 30/0.03. So the current values
   may already be right for the wrong reason. Worth an A/B to settle it with a measurement instead
   of an inference.
