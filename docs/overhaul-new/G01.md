## 3. Experiments

All experiment arms use one thin-LTO binary (`thin`, 16 codegen units, `--offline`) with
test-only environment switches, so A and B differ only in their environment; runs alternate
A, B, …. The switches are removed before any kept commit.

### E1 — cadence gate off when the display runs at the stream's rate (`SE_G01_CADENCE=auto`) — DISCARDED

Hypothesis (from reading `b0183dd`/`6faa359`): with `autoFrameRate` off the display is created at
the client's rate, so there is nothing to coalesce and the ¾-period gate only discards
jitter-early frames.

| arm | small window p50 / p90 / p99, fps | large area p50, fps | hi-res p50, fps | host |
|---|---|---|---|---|
| A (`cad-A-1`) | 20.2 / 23.9 / 33.3, 24.8 — `<video>`, second offer (lost answer) | no stamps (stage on the wrong display) | 31.8, 59.5 | invalid for latency: two displays |
| **B (`cad-B-1`)** | **777 / 1920 / 2189, 111 fps** | 381 (loaded) | 2044 (loaded) | ring dropped 187 frames, page `hostToPaint` p50 2.0 s |
| A (`cad-A-2`) | 27.6 / 33.1 / 35.9, 53.4 | 31.4, 52.8 | 34.7, 59.0 | |

Reading the host logs afterwards changed the explanation, not the verdict. The B run was taken
while **two** virtual displays were attached machine-wide (the shared driver reported
`machine [0, 1]`: another slot's released monitor was still attached) — and so was `cad-A-1`
after its retry. With one display attached (every other run: `machine [0]`), WGC delivers ~64
frames a second at 60 Hz and the gate drops almost nothing (`frames_skipped_cadence` 44–51 in a
whole ~110 s session, ≈ 0.5 a second). With two attached, the same 60 Hz display delivers
**175–190 frames a second** (`cad-B-1` encoded fps 175 with the gate off; `cad-A-1` skipped ~127 a
second with it on), and without the gate the encoder and the client get all of them: the ring
drops frames, the client's decoder backs up, and latency goes from ~28 ms to 0.8–2 s.

So: on a single display the gate is close to a no-op (not worth an A/B — at 0.5 frames a second
it cannot move a p50), and with two or more displays it is the only thing between the stream and
a 3× overload. **Kept as it is.** One B run was enough to see the overload; the other two were
cancelled to save display creations.

**Finding for "streams degrade with 2+ virtual displays":** with ≥ 2 IDD monitors attached, DWM
composes each at ~3× its nominal 60 Hz (G04 found why: the internal panel goes to 360 Hz). Every
one of those frames is a full-surface copy into a WGC frame pool and a callback, per display,
even when the gate then drops it. E5 cuts it inside WGC.

### E5 — WGC `MinUpdateInterval` 12 ms with **two virtual displays attached** — KEPT, as ⅔ of a period (the old app's value)

**This is the only mitigation available to us for the 2+-display degradation.** G04 established
the mechanism behind E1's observation: the owner's internal panel runs at 60 Hz with exactly
one virtual display attached and at **360 Hz with two or more**, so DWM composes each 60 Hz
virtual display about three times too often. Fixing that at the source would mean changing a
display we did not create. What we control is how often WGC hands us those compositions.

Request: `two_clients`, small window (client A joins; B joins as a second browser → two displays;
three settings edits on A while B is measured; then A measured with both attached). One run per
arm, A first, both on `machine max=2` (two displays) for the measured part. CPU 52 %, free memory
2.7–2.9 GB.

| | A: 4 ms (`r6-A-1`) | 12 ms (`r6-mu12-1`) |
|---|---|---|
| **WGC deliveries to the second session (B, 60 Hz), two displays attached** | **~190 / s** (encoded 63–67, `frames_skipped_cadence` +125 / s) | **~70 / s** (encoded 63–69, skipped +7 / s) |
| B before A's edits, p50 / p99, fps | 30.6 / 39.7, 58.0 | 29.1 / 44.6, 54.4 |
| B during A's edits, p50 / p99, fps, longest gap | 19.6 / 43.3, 55.5, 136 ms | 21.5 / 34.6, 58.0, 62 ms |
| A after B joined (A now at 120 Hz after its edits), p50 / p99, fps | 24.0 / 34.7, **91.7** | 22.6 / 33.7, **64.7** |
| single-display small window p50 (same join) | 27.1 | 27.6 |

Reading: the 12 ms floor cuts what WGC delivers in the 2-display state by ~⅔ — every one of those
frames was a full-surface copy into the frame pool plus a callback — with latency the same within
noise on every window (one run per arm; the ration allows no more). But a **fixed** 12 ms floor
caps a 120 Hz session near 83 fps: A, moved to 120 Hz by its own edits, painted 64.7 fps against
91.7. So the kept form is the pre-overhaul one, a floor of **⅔ of the stream's own period**
(11.1 ms at 60 fps, the measured arm to within 1 ms; 5.6 ms at 120), never under 4 ms. It
replaces the flat 4 ms that `ff8bfff`-era code set on the theory that the display composes at
its nominal rate. On one display it is level (E3).

Side effect, by reading: cursor-exempt frames are also bounded by it, at 1.5× the stream's rate
(90 fps for a 60 Hz client) — the bound the pre-overhaul host had when it measured 85 fps for a
pointer sweep, and the kind of cap the input report's P11 asks for. The 113 fps measured by
`6faa359` (with the 4 ms floor) is no longer reachable. Unverified: no pointer may be moved.

**E5-confirm — the committed binary** (`ea821a9`, thin LTO, no switches; `r7-A-1`, `two_clients`
+ small window + hi-res, one run). The run is contaminated: the first join's answer was lost
(`offers: 2`, `<video>`, a second session), so up to **three** displays were attached, and
`two_clients` reported "a client got no picture". What it does show: the 60 Hz sessions in the
2–3-display state skipped **~17–33 frames a second** at the cadence gate (4 ms: ~125), i.e. WGC
delivered ~80–95 a second instead of ~190 — the ⅔-period floor (11.1 ms) working as designed,
a little looser than the 12 ms arm. No latency number from it is usable.

It also showed, on one display, a **hi-res client now at 120 Hz** (G04's refresh fix is in
`d7a448a`): `2560x1440@120`, encoded 109–116 fps, ring drops ~1/s, p50 73.5 ms, 810 duplicate
frames painted. That state did not exist in any earlier G01 run (every earlier hi-res join was
at 60 Hz), so there is no G01 A to compare it with. By reading, the floor cannot cause it (at 120
fps it is 5.6 ms, still under the 8.3 ms period, and the 4 ms it replaced is equally permissive);
an encoder that drops ring slots and a client that paints duplicates point at encode/decode at
2560×1440×120 (G02/G05). **Not attributed; the orchestrator's re-measure of hi-res on the merged
head should include an A/B of `ea821a9`** (request in §7).

## 4. Defects

### D1 — WGC fails on a stale monitor handle and falls to a DXGI path that never delivers — FIXED, `VERIFIED` (forced)

Seen in baseline run 1 (`06e6fbb`, the hi-res join): the display was set to 2560×1440@60, the
ring encoder was built, then `GraphicsCaptureApi::new` failed with `Failed to convert item to
GraphicsCaptureItem` (`CreateForMonitor` refused the `HMONITOR` resolved moments earlier, before
the mode change settled). `start_on_monitor` fell straight to DXGI; DXGI duplication of an IDD
display on this hybrid laptop returns `ACCESS_LOST` on every acquire, so after 41
re-establishes it stopped with no frame ever delivered. The page saw no picture, timed out, sent a
second offer (`offers: 2`), and the renegotiation found WGC working: first picture 12.9 s after
the submit. Frequency: 1 of 48 handler-run logs that started a WGC capture at the time.

Fix: `start_live_capture` tags `ItemConvertFailed` with a `StaleMonitor` context;
`start_on_monitor` then sleeps 200 ms, re-resolves the display by name and retries, up to 5 times,
before DXGI is tried. Verified with a test-only switch that injects three `StaleMonitor` failures
through the same match arm (`SE_G01_FORCE_STALE=3`, removed before the commit): three retries
logged 200 ms apart, then the NVENC ring started on WGC, no DXGI, picture at 5.6 s after the
submit (answer 5.5 s), small window p50 27.0 ms. The natural failure could not be reproduced on
demand (rare, timing-dependent); what is verified is the recovery path.

### The hi-res regression (40 vs 32 ms against the old app) — not capture

Every hi-res join in this group's runs logged `virtual display … set to 2560x1440@60` although
the client asks for 120 Hz, and NVENC `rc=constqp qp=15` requested but `falling back to CBR`.
Two causes outside G01, both found:

- **60 Hz instead of 120 (G04 / handler).** The handler's hi-res join presents the device token
  minted by the 1080p join, the host finds a settings row for it ("re-presented a device token
  this host has settings for") with the 1080p join's 60 Hz recorded, and applies it.
- **CBR instead of constant QP (G02).** The handler's device override carries `videoQuality 15`;
  the old app ran that as constant QP 15, the current head silently as CBR (`supports_rc` bug,
  fixed on `g02` at `cf63279`, which measured hi-res p50 33.2–33.8 ms).

On the capture side the hi-res path is a native-size `CopyResource` into the ring slot (no
scaler, `downscale=false`), on the same adapter as the encoder, with the same frame-pool depth
(3) as the old app's ring; `scale` stage p50 0.15–0.26 ms in the host telemetry. Pool depth and
copy cost were therefore not experimented on.

- **The drain-to-newest frame pool and the matched `Recreate` buffer count** (fork, since

- Nothing in this group was found that measured well and was later reverted, apart from the

## 6. The cursor path, by reading

No agent may move the cursor, so nothing in this section was measured; every statement is from
the code at `06e6fbb` and the commit history.

**Default path (WGC draws the pointer).** `CursorCaptureSettings::WithCursor`; the host overlay
(`cursor_overlay.rs`, `d848234`/`0fa6f54`) is only built with `SE_CURSOR_OVERLAY=1`. Per delivered
frame, `on_frame_arrived` calls `CursorProbe::changed()` (`GetCursorInfo` + `MonitorFromPoint`,
no lock, no allocation) and passes a frame whose pointer moved, changed shape, appeared or left
this display past both gates: the dirty-region gate (only consulted with `autoFrameRate` on) and
the cadence gate (`6faa359`: exempt). Everything else on the capture side treats a pointer frame
like any other frame.

**What can make the pointer glitch, by reading:**

1. **The cadence gate, for the frame after the pointer stops** (also the input report's H9).
   `CursorProbe` reads the pointer when the callback *runs*, not when the frame was composed. If
   the pointer moves between a compose and its callback, that frame is reported "moved" and
   exempt; the next frame — the one that actually shows the final position — compares equal and
   meets the ¾-period gate. If it arrives early it is dropped and the pointer sits one position
   behind until the next kept frame (≤ 1 period on a moving desktop, up to the 200 ms keepalive
   on a still one — and the keepalive re-encodes the *held* slot, i.e. the stale picture). The
   gate cannot simply go (E1: the display delivers ~110–190 fps, and without the gate latency goes
   to ~1 s), so this remains. A fix that keeps the gate: on the first frame after a run of
   cursor-moved frames that reports "unchanged", let it through once (a "settle" frame). Not made:
   it changes what a pointer stop looks like and nothing here can move the pointer to see it.
   Written up as a later test in §7.
2. **The exemption runs a moving pointer at the compositor's rate** (input report H9 / P11): 113
   painted fps was measured for a 60 Hz client with the 4 ms WGC floor. On a weak decoder the
   client's drop-to-freshest-and-ask-for-a-keyframe rule would then fire while the mouse moves.
   **Partly addressed as a side effect of `ea821a9`:** the WGC floor of ⅔ of a period now bounds
   cursor-exempt frames at 1.5× the stream's rate (90 fps for a 60 Hz client) — the pre-overhaul
   bound under which the old host measured 85 fps for a pointer sweep. A tighter cap at exactly
   the client's period was not made (`6faa359` measured windows below the compose interval as
   worse than no gate, and nothing here can move a pointer to check). Test: §7.
3. **`CURSOR_SHOWING` tested with `==`.** `CURSORINFO.flags` is a bitfield (`CURSOR_SHOWING`
   0x1, `CURSOR_SUPPRESSED` 0x2 from Windows 8). For the documented values (0, 1, 2) equality and
   the correct bit test agree, and for 3 (showing *and* suppressed, not documented as occurring)
   equality also says "not drawn", which is right. Rewritten as an explicit bit test (showing and
   not suppressed) so it does not depend on no further bit being defined: behaviour-identical for
   every documented value, so it is a robustness edit, not a measured fix. It only affects the
   gating decision, never what WGC draws.
4. **GPU scheduling class.** `408099e` set the process to REALTIME and the owner reported a slow
   machine with a flickering pointer; `b0183dd` lowered it to ABOVE_NORMAL (3). The old app never
   called it (Normal, 2). Measured for latency in §3 (`SE_GPU_SCHED_CLASS=2`); its effect on the
   pointer the compositor draws is unverifiable without moving it.
5. **The overlay path** (`SE_CURSOR_OVERLAY=1`) is polled on the encode thread's idle tick, takes
   the keyed mutex with an 8 ms timeout, and in a scene where real frames keep arriving its idle
   arm never fires — the repo's own 59-vs-85 fps measurement. Left off by default; not touched.

Pointer behaviour that is not capture's (input injection, the client's pointer lock, H1–H8 of
`INPUT-REPORT.md`) is out of this group.
