### The hi-res regression (coordinator's question)

The orchestrator's measured regression is hi-res p50 40.1 ms (head) vs 31.9 ms (old app). The
client video path cannot be where those ~8 ms live:

- **arrival → paint at hi-res is 1.0–1.1 ms p50** on the head page (worker clock: frame read off
  the transform → `drawImage` call), and **decode p50 0.95–1.33 ms**, in every window above. Even
  a decoder or worker twice as slow would cost ~1 ms.
- **The old page's worker under the new page** (k02) and **the old page's transport** (k03,
  `createEncodedStreams`) both measure the same as the head (§3 table).
- **Canvas sizing at DPR 2**: both workers size the canvas backing store to the frame
  (`frame.displayWidth`, 2560×1440) and let CSS scale it; the old one latches the size on the first
  frame and uses the 5-argument `drawImage` with the same size, the new one re-checks per frame
  (no change after the first) and uses the 3-argument form. No resize happens per frame in either.
- **Profile / CABAC decode cost**: the client stats report the negotiated payload as `42e01f`
  (constrained baseline) on the head too; the worker configures `avc1.640034` only because of the
  inert codec-hint wait (above). WebCodecs decode cost is ~1 ms at hi-res either way.
- **Hardware vs software**: `decoderHardware` true on every window; the NVIDIA decoder engine
  reads 0 % throughout, i.e. headless Chrome decodes on the Intel iGPU of this hybrid machine,
  old and new alike.
- **Per-frame worker work**: one `Map` set/get, three ring-buffer pushes and an rAF-free paint;
  the A/V and size messages are rate-limited (200 ms / on change).

So the regression is upstream of the client page: host capture → encode → send → network → the
transform (the page's `hostToPaint` 17–21 ms minus 1 ms on the client). Hand to G01/G02/G03.
One client-side contributor the host owns: the keyframe storm (D3) makes the host encode an IDR
~3×/s, and an IDR at 2560×1440 is the largest frame the encoder makes; with D3 fixed, hi-res p50
moved 32.9 → 32.05 and the encoder load fell 4–7 points, which is within noise for p50 here.

## 4. The keyframe storm, client half (D3)

Cause, confirmed on every WebCodecs session: inbound-rtp `framesDecoded` 0, `keyFramesDecoded` 0,
`pliCount` +28–35 per 10 s window, and the worker's own `keyframesIn` rising in step (~3/s): the
host answers nearly every PLI. libwebrtc's VideoReceiveStream gets no frame because the transform
consumes them; it asks for a keyframe each time its 200 ms keyframe wait expires.

Options evaluated:

| option | PLIs / 10 s | cost | result |
|---|---|---|---|
| nothing (head) | 28–35 | ~3 IDRs/s from the host | — |
| hand **every** frame back to `transformer.writable` | 0 | libwebrtc decodes every frame a second time (framesDecoded = frames received); 5 of 6 windows on that run were CPU-loaded | rejected |
| hand **keyframes** back | 3–4 (one per ~3 s: the receiver then waits on its 3 s frame timeout) | one extra decode every ~3 s | **kept** (`a00083d`) |
| request real keyframes out-of-band only (opcode 0x64) instead of `sendKeyFrameRequest()` | — | — | not measured: on the current host it changes nothing (libwebrtc's PLIs continue regardless); it only pays off together with a host change (below). Left as a recommendation. |
| anything in the spec to silence the receiver's requests | — | — | none exists: `jitterBufferTarget`, `playoutDelayHint` and the encoded-transform API have no control over VideoReceiveStream's keyframe requests |

Coordination with G03 (their ledger `docs/overhaul-new/G03.md` on `g03`, `PliBackoff`): the host
fix must stand alone (the relay serves an older page). With this page change the residual PLI rate
is one per ~3 s. G03's backoff windows cap at 2 s, so a request every 3 s is still admitted: such a
client would get one IDR per ~3 s rather than none. Two ways to remove that, both host-side and
both G03's call: (a) widen the cap above 3 s, or (b) G03's own proposal — have the page request
genuine keyframes out-of-band and let the host ignore PLI/FIR from a client whose STATS say
`transport_tier != 0 && key_tier == outOfBand`. (b) needs a small worker change (prefer
`requestKeyOutOfBand()` over `sendKeyFrameRequest()` once the PONG bit is set) that I did not make,
because without the host half it only changes the reported tier.

## 5. Defects

**D1 — the page demotes itself to `<video>` after WebCodecs is already painting. FIXED (`9aae1d3`).**
Mechanism: `armFrameWatchdog` is reached from two handlers (ICE `connected`/`completed` and
`pc.connectionState === 'connected'`), and the only thing that clears the watchdog is the worker's
single `'rendered'` message via `onStreamLive`. Any arming after that message — the other handler,
ICE `connected` → `completed`, a transient disconnect that recovers, or simply the `'rendered'`
message being dispatched *before* the state-change event (they come from different task sources,
so under a busy main thread their order is not guaranteed) — leaves a watchdog nothing clears, and
5 s later `fallbackToVideo` sends a second offer. Evidence on the head: 2 of 56 handler runs on
10/5 (`2026-10-05T04-47-40-229Z-slot2-50104`, `…04-48-04-571Z-slot3-45812`) logged "falling back to
<video>: no WebCodecs frame within 5s" ~5.4 s after the answer, with the paint hook having already
counted 178 painted frames, then `offers: 2` and videoPath 3 for the rest of the session. Every
such demotion is also a stream rebuild, which the input report says resets the raw-movement flag
(the session continues on the tracked pointer path) — so this is a cursor fix as well.
Fix: a per-session latch (`webcodecsPainted`, set by `'rendered'`, cleared by `teardownSession`);
neither the arm nor the timer acts once it is set. Regression test
`scripts/test-client-watchdog.mjs` (in `pnpm test:client`) lifts the functions out of the page and
drives them on a fake clock: 4 of 7 assertions fail on the previous page.
Live status: in 23 joins on binaries carrying the fix (X1, X2, the final build) no demotion and
one peer connection per session; the four X2 joins carried a log line for a suppressed re-arm and
it never printed, i.e. the race did not occur in them. At 2/56 on the head, a confirmation run would need tens of
joins; not affordable under the display ration. **Live-unverified; harness-proven.**

**D2 — a lost or refused WHEP answer demotes the session to `<video>` for good. FIXED by G07
(`2dda493`, `setupFailureAction`); my parallel fix was dropped on the rebase.** What I had found:
`start()`'s catch called `fallbackToVideo` for every setup error, including the WHEP deadline
(the lost-answer defect, ~1 join in 5 on a busy host per the handler README) and a 500 from a
display that did not attach. Seen in the baseline's `fallback_paths` default tier. Now
`isHostSideSetupFailure(err)` errors re-offer once on the same path (bounded, reset when live); a
second failure and every other error take the ladder exactly as before. (That was my version;
G07's is equivalent for the WHEP deadline, 5xx and dropped connections.)

**D3 — keyframe storm, client half. FIXED (`a00083d`)**, §4.

**Open, not mine:**
- The lost answer itself and the second session/display it causes (G04/G07).
- Slow joins: answer 3–8 s, first picture up to 13.7 s on a first join (k01), G04/G01.
- `5e2dff0`'s codec-hint wait is inert (always times out before the answer). Harmless; could be
  removed or re-armed from the answer, left for the owner (no measurable effect either way).

**The ~10 % checksum failures at 1080p (investigated, then handed back).** Decoding the stamp's 8
rows separately (a temporary `stamp_diag` reader, not committed) showed nearly every frame torn
horizontally inside the strip: upper rows carrying a stamp 4–10 ms newer than lower rows, at
1080p and at hi-res alike; the cell-height average reads a tear near the middle as grey cells (the
128-luminance cells in every failure example) and fails the check. The stage drew with GDI+ at
~100 draws/s, and the compositor caught draws half done. Same conclusion as the orchestrator's,
fixed on `latency-overhaul-new` by `stamp_band: "center"` (`ef8b923`), so my diagnostic and an
alternative GDI `BitBlt` stage were dropped. Not an app defect.

## 6. Lost optimisations

- **`desynchronized: true`** (old page, removed by `fd2c1d0`): the head's
  `getContextAttributes()` reads `desynchronized: false`; Chromium's low-latency canvas path is on
  `HTMLCanvasElement` only, so on the worker's `OffscreenCanvas` it is inert either way, and its
  effect would be after the paint call, which the stamp metric does not include. **Ruled out as
  measurable here**; not restored.
- **5-argument `drawImage`** (old page): same size as the frame, so no scaling either way; the old
  worker as a whole (k02) measured the same. Not restored.
- **Old backlog policy (`decodeQueueSize`)**: neither policy trips on this machine; nothing to
  recover.
- **`createEncodedStreams` transport** (what the old page actually ran on Chrome): measured equal
  at hi-res (k03). Not restored; the script transform keeps `sendKeyFrameRequest()`.
