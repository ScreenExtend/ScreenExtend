# G02 — Windows encode (NVENC, the async ring, x264, encoder settings)

Branch `g02`, from `latency-overhaul-new` (merged up to `b9622f9`, handler changes only). Agent:
G02 (Opus 5.5). Machine: Windows 11 26200, RTX 3080 Ti Laptop (hybrid), Chrome 154 headless,
2026-10-05.

## How the numbers were taken

- **Handler A/B** (`scripts/test-handler/handler.mjs`): every arm ran **the same binary**,
  differing only in a host environment variable, interleaved (ABBA order) by a small runner.
  Binaries: `exp1` = `80e00a4` + the constant-QP fix + temporary `SE_X_*` switches; `exp2` = `exp1`
  + `SE_X_FORCE_CBR`. Thin LTO / 16 codegen units (one binary per comparison, so the profile cannot
  bias it). The `SE_X_*` switches were never committed.
  - `SE_X_FORCE_QP=N` forces constant QP N; `SE_X_FORCE_CBR=1` forces CBR even with a device override;
    `SE_X_LDKFS_PRESET=1` keeps the preset's `lowDelayKeyFrameScale` (1, as the old app did) instead of 2;
    `SE_X_PROFILE=baseline` forces Baseline/CAVLC in the encoder; `SE_NVENC_NO_ASYNC=1` (shipped).
  - Windows marked `loaded`, or above 75 % CPU, or joins with `offers > 1` are discarded and listed
    as such. Every run recorded commit headroom and free memory before and after (≥ 3 GB headroom
    and ≥ 1.9 GB free at every window start).
- **Bench** (no display): `g02x_serial_ring_encode_time`, an ignored test in the experiment tree,
  run from the release test binary under the handler's `measure.lock` so no other agent's window
  overlapped. Ring of 3 shared textures exactly as the live path (keyed mutex, `encode_input_slot`,
  depth 1). Content: a static synthetic gradient with a 64 px box moving each frame (screen-like:
  small change per frame), IDR forced every 40th frame, 8 ms between frames, 380 measured frames
  per config. Bitrate = the live formula (`w*h*fps/10`, 12.44 Mbps at 1080p60, 22.12 Mbps at 1440p60).
  "NVENC time" = `encode_input_slot` duration **after** the upload to the slot has completed on the
  GPU (event query), i.e. keyed-mutex acquire + map + encode + lock + copy-out + unmap. Byte counts
  are deterministic; times are bimodal on this laptop (GPU clock state) so ranges are given.

## IDR cost (for G03)

Bench numbers, same content, 9 forced IDRs per config, ×2–4 runs. NVENC time is the clean one
(upload excluded). One IDR replaces one P frame, so its extra cost is IDR − P.

| config | P bytes | IDR bytes | NVENC P p50 | NVENC IDR p50 | extra per IDR |
|---|---|---|---|---|---|
| 1080p CBR 12.4 Mbps, scale 2 (shipped) | 11.0 KB | 42.3 KB | 2.3–3.5 ms | 2.4–3.8 ms | +31 KB, +0.1–0.5 ms |
| 1080p CBR, scale 1 (old app) | 12.9 KB | 24.5 KB | 2.5 ms | 2.4–2.8 ms | +12 KB, ≈ 0 ms |
| 1080p CQP 23 | 0.3 KB | 44.9 KB | 2.7–3.5 ms | 2.6–3.8 ms | +45 KB, +0.1–0.4 ms |
| 1080p CQP 15 (owner's setting) | 0.2 KB | 83.0 KB | 2.1–3.1 ms | 2.8–4.3 ms | +83 KB, +0.7–1.1 ms |
| 1440p CBR 22.1 Mbps, scale 2 (shipped) | 18.9 KB | 72.6 KB | 4.9–5.7 ms | 6.0–6.5 ms | +54 KB, +0.5–1.0 ms |
| 1440p CBR, scale 1 | 22.0 KB | 43.3 KB | 5.5–7.3 ms | 5.6–5.9 ms | +21 KB, ≈ 0 ms |
| 1440p CQP 15 | 0.3 KB | 143.9 KB | 4.9–5.3 ms | 4.5–7.0 ms | +144 KB, +0–2 ms |

At the storm's ~3–4 IDR/s, shipped 1440p CBR spends ~0.2 MB/s (≈ 1.7 Mbps) on IDRs alone, and
with the owner's QP 15 ~0.5 MB/s (≈ 4 Mbps); each IDR is a burst of 50–100 MTU packets. On loopback
this does not show in the stamp metric (E3); on Wi-Fi it is queueing delay on every IDR.
**The encoder does the right thing when asked:** a keyframe request is a flag (`idr_requested` /
the shared `idr_request` atomic), consumed by the next encoded picture — in `stage()`, in
`take_idr_request`, or by the idle keepalive — so N requests between two pictures produce one
IDR and there is no backlog. Host telemetry agrees: `keyframe_requests` 354–385 vs `idrs_sent`
355–382 per hi-res session (the gate suppresses ~2; every admitted request became exactly one IDR).
`nvenc_repeat_honours_a_pending_idr_request` passes (a request on a static desktop is honoured by
the keepalive, the `9c4499a` fix).

## Lost optimisations

- Long-term references / ref invalidation (`f66a5a7`, `240f9f6`, disabled by `abd1d2c`/`9ffd3ad`):
  ruled out here. The disable is correct (SPS `max_num_ref_frames` cannot cover the LTR set; green
  surfaces on hardware decoders), and with the keyframe storm every loss is answered by an IDR
  anyway. Re-enabling needs the SPS rewrite `SE_NVENC_LTR=1` was left for. Not run (`SE_NVENC_LTR=1`
  would risk the green artefact the owner reported; no display budget left for a visual check).
- Rolling intra refresh (`d996635`, off by `9ffd3ad`): not run, same reason (`SE_INTRA_REFRESH=1`
  is the documented green-band cause).
- `lowDelayKeyFrameScale` 2 (`f66a5a7`): see E3 — the old value (1) halves IDR size; no loopback
  latency effect. Not changed, because the IDR's lower quality persists for several frames and the
  storm fix (G03) removes most IDRs; G03 should decide with this table.
