Laptop (hybrid), real panel 1920x1080@360. Every number came from

## 1. The headline defect: "changing a device's settings makes two new devices appear with two virtual screens"

### Reproduced, and how

The CLI path (`devices set`, one setting class at a time) **does not** produce it on the head
when the renegotiation succeeds. Head, run `09-53-07-062Z-slot1` (handler fixed to address the
live join, see §6): every stream-class edit (quality, video scale, refresh, DPR, orientation)
cost exactly one in-place renegotiation (1 new peer connection, 2 `/whep` requests: POST +
PATCH), with 1 join and 1 display before and after, the same join id and display id, no device
removed or added, and the picture back in 0.8–2.0 s. Audio, display scale and name cost nothing
(no PC, gap ≤ 110 ms). A second orientation edit is inert because `autoOrientation` defaults on.

It **does** appear as soon as one in-place renegotiation **fails**. Here is the chain, read from
`start_session` and then reproduced:

1. A continuing join (the page renegotiating on its join id after an epoch bump) fails. Possible
   causes are a capture-start error after the mode change, a WHEP activation error, and so on.
2. `abandon_failed_attempt` called `session::remove_session`. The display id lived only in that
   entry, so the display was orphaned: nothing ever removes it until the host exits.
3. The previous attempt's teardown task wakes after its grace period and checks
   `is_current_session`. That check reads a *missing* entry as "superseded", so it logs
   "superseded; keeping display" and keeps it too. No `DeviceRemove` is ever sent, so the old
   dashboard row stays.
4. The page answers the failure by offering again on the same join id (`fallbackToVideo` →
   `start(false, true)`). `continuing_join` finds no session, so it is a **fresh join: a second
   display and a second dashboard row**.

Reproduction: a one-shot injected failure on the first renegotiation
(`SE_G04_FAIL_RENEGOTIATION=1`, experiment build only), `settings_change`. Both arms used the same
binary.

| arm | after the first stream edit (video quality) | rest of the run | at host exit |
|---|---|---|---|
| head behaviour (`SE_G04_LEGACY_ABANDON=1`), run `11-01-30-926Z-slot3` | joins 1→1, **displays 1→2**, **join id changed**, `DeviceJoin` +1, 3 PCs / 5 `/whep` | display 0 logged "superseded; keeping display" every edit, never removed; its row never removed | `defectSeen: true` |
| fixed, run `11-11-59-345Z-slot2` | joins 1→1, displays 1→1, same join id, same display id, 0 rows added or removed; retry reused display 0, picture back in 2.4 s | normal | `defectSeen: false` |

This is the owner's symptom: old row + new row, old screen + new screen. **Kept: fix 1** (below).
Note that the handler's CLI edits never fail on their own, which is why no earlier run saw it.
What makes a renegotiation fail on the owner's machine is not established. Candidates are G01's
WGC `ItemConvertFailed` after a mode set, and a DXGI fallback that cannot duplicate on hybrid
graphics; both sit downstream of a mode-changing edit.

### Other routes to the same symptom found while reading (fixed or written up)

- **A superseded attempt that completes anyway** (fix 2): two offers on one join, where the
  page's 10 s `/whep` timeout fired and it retried. The older attempt passes the two existing
  supersede checkpoints and goes on to activate, report and `set_active_capture`. That
  overwrites the newer attempt's stopper, so one capture+encoder is never stopped (a leak).
  Fixed by checking again after the join of the two halves and after `activate_whep`.
- **A failed fresh join leaves its display** (part of fix 1): if `start_on_monitor` failed after
  the display was recorded, the display was orphaned the same way. Now removed with the session.
- **The relay's old client page** (fix 5, UNVERIFIED, not run): a cross-network client gets the
  relay's own older page, which renegotiates *without* a join id. Every settings edit then becomes
  a fresh join with a second display and row, while the first waits out its grace. With two joins
  under one relay `client_id`, `/reconfig` answered from an arbitrary one (`.next()` on a
  HashMap), and half the time that was the stale join, which the page reads as another
  reconfigure. Fixed by resolving a relay client to its live join, and by treating a joinless
  relayed offer from a client whose join is still streaming as that join renegotiating. Unit test
  only; no relayed session can be driven here. **If the owner joins over the cloud URL, this is
  the most likely cause of the report.**
- **The GPU-encode toggle dropped every session** (fix 6, G09's finding #1, verified by reading):
  `set_disable_gpu_encode` ran `restart_streamers`, which sends every client a `HostExit` bye
  and restarts the servers. Each device that came back did so as a fresh join on a fresh display
  (+68 MB of driver leak each, §3). The pipeline reads the flag live
  (`Config::software_encode_now`), so a restart is not needed: every live join now renegotiates
  in place. `RELOAD` (`config set disableGpuEncode …`) now applies it to a running host, so the
  CLI can reach it. The port change still restarts the servers, which is unavoidable for a bind.

### Does the desktop UI path differ from the CLI path?

Both end in the same Rust functions (`set_device_override`, `set_device_pointer_scope`,
`set_device_auto_frame_rate`, `set_device_adaptive_modes`, `set_device_audio_output`). The CLI
reaches them through `RELOAD` → `apply_saved_devices`, which replays every saved row; the sheet
calls only the commands whose values moved. The differences that matter:

1. **The sheet emits its own `deviceModify`** (`device-details.tsx`), with `joinId:
   device.joinId` of the row it was opened from. `App.tsx`'s listener *appends* a row when no
   row has that join id (`index < 0 → [...prev, device]`). If the host's renegotiation failed and
   came back as a new join (route 1 above), the host's `DeviceJoin` adds a row for the new join
   and the sheet's own emit cannot match it. If the old join had been removed first, the emit
   would **resurrect the old row**. Either way the UI shows two devices where the CLI log shows
   one `[dashboard] device joined`. This is UI-only and out of scope here. It is written up for
   the UI job: the sheet should not emit `deviceModify` itself (the host already sends
   `DeviceModify` for an in-place renegotiation, and nothing for a no-op save).
2. **One save can bump the epoch twice** (`set_device_override` and then
   `set_device_adaptive_modes` or `set_device_auto_frame_rate`). The page ignores a second epoch
   change while `reconfiguring` is set, so a setting that lands after the offer was read is
   silently not applied until some later renegotiation. It is not a duplicate. Client page
   (G07): recommend re-polling `/reconfig` once a rebuild completes and acting on any epoch
   newer than the one it rebuilt for.
3. **Field fallbacks** (G09 #3): `apply-config.ts` fills a saved row that lacks `videoQuality` /
   `remoteControl` with 23 / false, while the CLI replay and the host's `Device::defaults` use 15
   / true. A row written by an old version therefore runs at a different quality, with remote
   control off, in the GUI than under `serve`. A config-editor apply after a `RELOAD` compares
   unequal, which costs one renegotiation. It is not a duplicate. UI job: align the TS fallbacks
   to 15 / true.
4. **GUI start ordering and auto-approve** (G09 #2): the GUI approves every joined device, so
   its rejoin is on the pre-approved path, and the presented token is kept. That is the same
   identity the CLI path gets via `is_known_device` once an override row exists, so I found no
   duplicate route there. The refused-OTP window at start-up only refuses; it does not duplicate.

**UI-job reproduction** (needs the desktop UI, a mouse and the owner's permission): open the
desktop app; join one browser tab (LAN URL); open the device sheet from the Devices page; change
*refresh rate* and save; watch the dashboard row count and `ScreenExtend status --json`
`telemetry.joins`. Repeat with a relayed client (cloud URL). Pass: one row, one display, the
same `joinId` before and after. Also run it with the host started from a build carrying
`SE_G04_FAIL_RENEGOTIATION=1` (see §5): expect one row/one display on this branch, and two on
`latency-overhaul`.

From every timestamped `serve.log` (79–89 fresh joins, 05:06–11:12Z, all builds since

|---|---|---|---|

| create → monitor attached (Windows/IddCx) | 1352 ms | 1405 | 1737 |
| forced mode set (`ChangeDisplaySettingsEx`, display already at that mode) | 172 ms | 336 | **3696** |

The old app spends the same: attach 1.33–1.40 s, the same forced mode set and DPI loop (both

## 3. The virtual display driver leaks (coordinator's top-priority item)

Read-only sampling of `WUDFHost.exe` pid 1964 (the IddCx host for `VirtualDisplayDriver.dll`)
every 2 s for 70+ min, lined up with every run's timestamped driver events:

| event | Δ handles | Δ threads | Δ commit |
|---|---|---|---|
| display create (attach + first mode), n=63 | +46 | +6.5 | **+67 MB** (≈47 MB for 1080p, 94–124 MB for larger ladders) |
| display remove, n=63 | ≈0 to −10 | ≈−1 | ≈0 (gives back almost nothing) |
| in-place mode change (60→120 Hz on a live display) | +27 | +6 | **+47.6 MB** |
| shared-driver list notify (n=189), host start (n=36), pipe connection | ≈0 | ≈0 | 0 |
| renegotiation without a mode change, scale-live, name/audio edits | 0 | 0 | 0 |

Over 70.6 min: +4.29 GB, +2388 handles, +361 threads, for 63 creates (over 140 min: +8.45 GB,
+4735 handles, +713 threads). A removal while other virtual displays stay attached sometimes
also leaked one mode commit's worth (+27 h / +47 MB), presumably the re-layout of the remaining
displays. Net per 1080p
create→remove cycle: about **+27–37 handles, +4–5 threads, +47 MB, never returned**. At the
coordinator's 04:00 reading (20 GB, 11,970 handles) that is ≈ 430 cycles, which fits tonight's
count. Skipping the redundant same-mode set at create (fix 4) did **not** change the
per-create figure. The final build's first create (mode set skipped) leaked +37 handles,
+5 threads, +46.5 MB, the same as before. So the cost is in the monitor arrival and its
swapchain, and in each *real* mode commit, not in the list traffic or a no-op mode set.

- **It is a product defect, not a harness artefact.** A normal (non-shared) host sends the same
  driver operations for every join, rejoin and mode-changing edit. The shared-driver mode's
  extra notifies leak nothing. A host left running for days leaks ~50–70 MB per join and per
  mode change, and the commit charge is the machine's, not the app's.
- **Join time does not track it.** `display=` averaged 1.9–2.1 s from the first handler runs
  (02:28Z) to the last (11:12Z), while the leak grew by many GB, and the attach step was a flat
  1.33–1.40 s. The 2+-display degradation was not reproduced on a quiet machine (below), so I
  could not correlate that either.
- **What our side can do without a new driver:** create fewer monitors and do fewer mode
  commits. This branch removes the duplicate display of route 1 (one extra create per failed
  renegotiation), the toggle-drops-every-session path (one create per device per toggle), and the
  relayed joinless renegotiation (one create per settings edit for a relayed client). Further
  candidates, not done: adopt a display still in its disconnect grace for a fresh join from the
  same device token (a page reload after a lost link), and do not re-create on a refresh change
  that a registered mode already covers (already the case).
- **What needs the owner (admin):** only a device restart or a reboot frees what has leaked.
  `pnputil /enum-devices /class Display` (or `Get-PnpDevice -FriendlyName '*Virtual Display*'`)
  gives the instance id; then `pnputil /restart-device "<instance id>"` from an elevated prompt,
  with no ScreenExtend host running. The fix itself is in the driver (`virtual-display-rs` fork,
  `src-tauri/resources/PROVENANCE.md`): the swapchain/monitor objects of a departed or re-moded
  IddCx monitor are not being released. That needs a driver rebuild and re-signing, so it is
  UNVERIFIED and for the owner.

## 4. Other findings

- **Seeded refresh rate pinned for life** (fix 3). `f569e41` seeds an override row at a device's
  first join so that a first save compares equal. Every later join read that row's refresh rate
  back as the device's *setting*, so a device that first joined at 60 Hz (or while the page's
  rAF measurement was throttled) streamed at 60 for the life of the host, whatever it reported
  afterwards. The old app used the reported rate on every join until a user saved one. Fixed: a
  seeded rate is a detection until `set_device_override` makes it a setting.
  Measured on the hi-res scenario after the handler fix (same token as an earlier 60 Hz join,
  client reporting 120 Hz). Pinned (old behaviour, `SE_G04_STICKY_REFRESH=1`): 2560x1440@60,
  painted 57.5 / 57.4 fps, p50 38.0 / 38.4 ms (the second window was flagged loaded). Fixed:
  2560x1440@120, painted 72.5 / 86.1 fps, p50 42.1 / 35.1 ms (base 2 / arm 2 above). Kept as a
  defect fix: fps is higher and p50 is within noise. One fixed window had p99 124 ms, the other
  46 ms. G01's coordinator note asks whether this is "a saved override or what a join landed
  on": it was the latter. The GUI auto-saves only `knownDevices` on a join, not `devices[]`, so
  in the GUI the seed now stays a detection until the sheet is saved.
- **The "120 Hz client capped at 60" finding was mostly the handler's.** The standard hi-res
  scenario reuses the 60 Hz browser, and `setClient` never re-pinned `screen.refreshRate`, so
  the page reported 60. `DEFAULT_MAX_AUTO_REFRESH` had already been removed by `170138e`. The
  handler is fixed (§6), and fix 3 covers the product half.
- **Two displays degrade the stream: the mechanism is the owner's own panel changing refresh
  rate** (display side, OPEN, no fix in code). I sampled `QueryDisplayConfig` read-only every
  2 s through the final verification run (scratch `dispcfg.ps1`, `dispcfg.jsonl`). The internal
  360 Hz panel (target 8388688) reads 360.006 Hz with no virtual display. With **exactly one**
  virtual display attached it reads **60.003 Hz** (13:20:22, 13:25:10, 13:27:50, 13:28:10Z:
  every single-display interval). With **two or more** it is back at 360 Hz (13:24:12–13:25:07,
  13:25:28). The virtual targets report exactly their own modes (60 or 120 Hz, vSync equal), each
  on its own source, extended, not cloned. This is the mechanism behind G01's measurement (one VD:
  ~64 fps delivered; 2+ VDs: ~175–190 fps per 60 Hz display). With one VD, DWM's clock is the
  panel's 60 Hz; with two, DWM runs at 360 Hz and composes each IDD display at a sub-multiple, and
  every compose is a full-surface copy into the capture pool. It also means **the owner's laptop
  screen runs at 60 Hz whenever exactly one device is connected**. `b0183dd`'s "the real
  desktop's cadence collapsed from 357 fps to 60" was attributed to a 360 Hz client display, but
  this is what it saw. My explanation, not proven: Windows' per-topology persisted configuration
  (the CCD database) has 60 Hz for the panel in the topology "panel + one VirtuDisplay", and the
  IDD monitor's identity is the same on every attach (UID256), so the persisted topology is
  re-applied each time. The earlier two-clients run on the head (`09-20-23-310Z-slot4`,
  `bUntouched` true, A 24.2 ms / 88 fps after B joined) did not show a latency collapse on a
  quiet machine, so how much this costs end to end at 2 displays is still unmeasured. Fixes
  (owner's decision, §9): the owner sets the panel back to 360 Hz once while one device is
  connected (which should persist for that topology; untested), or the host restores the user's
  panel mode after an attach (needs the "never write a display we did not create" rule relaxed for
  "restore what it was"), or G01's WGC `MinUpdateInterval` throttle treats the symptom.
- **The leave beacon is often not received** (client page, G07). In `leave_rejoin` and
  `slow_answer` the host frequently logged no `leave beacon` after `Page.navigate('about:blank')`.
  The display then lived until ICE failed (~34 s) plus `LEAVE_SETTLE` and the 10 s grace, about
  45 s, which was flagged as "second session/display" on the next join. `sendLeave` returns
  early when `!isLive || reconfiguring`; the old app has the same gate. Recommend that `pagehide`
  release a held join id unconditionally.
- **The lost answer** (baseline agent / G07): reproduced once on a quiet machine
  (`09-20-23-310Z-slot4`). The host generated the answer 2.52 s after the request, and the
  browser's POST never received headers and was aborted at 10 s. The retry went out on a reused
  h2 connection and succeeded in 2.5 s. The retry was a fresh join with a new token and a second
  display, because the page held no join id; the first display lived ~42 s, until ICE failed and
  the grace ran out. The host cannot recognise the retry as the same tab without client help.
  Recommend (G07) a per-tab id generated at page load and sent with every offer, which the host
  could map to a session that has never connected.
- **The input injector's display lookup** (coordinator lead 1): the session hands the injector
  `InputParams.device = Some(device_name)`, the `\\.\DISPLAYn` GDI name captured at create
  (`prev.device_name` on a renegotiation), and the injector re-resolves that name every 500 ms.
  The stable identity (`LiveDisplay.device_path`) exists on the session side, but `InputParams`
  (in `webrtc_session.rs`, G03) has no field for it, and the lookup is in `streamer/input/`
  (frozen). For the later input job: add `device_path` to `InputParams`, and have the injector
  resolve it through `virtual_display::resolve_owned_display` (path → current GDI name) and
  refuse to inject when it does not resolve, instead of falling back to the whole desktop.
- **Rebuild count per settings change** (coordinator lead 2): on the CLI path every stream-class
  edit is exactly one renegotiation (one PC, two `/whep`); cosmetic, audio and scale edits are
  zero. The routes fixed above each removed one or more extra rebuilds (a fresh join with a new
  display per failed renegotiation, per GPU toggle, and per relayed edit).
- `2dba8b9` (correlate the new display by friendly name): **inert on this machine**, with 0 of
  136 attaches named directly. Every monitor's EDID name is `VirtuDisplay+`, so the match is
  always ambiguous and the 100 ms poll does the work. It costs one `QueryDisplayConfig`. Left
  in; not a win.
- `driver_ipc/sync/client.rs` (G09 #4): the two `log::error!` calls went nowhere and are now
  `teprintln!`. The `Drop` one also had its test inverted: it reported "receiver panicked" on
  every normal drop (`Err(Empty)`), and now reports only an actual panic payload.

  when two joins share a name. After a retried join, the settings test had been editing the
  dead first join's token ("0 live session(s) will renegotiate"), so `settings_change` measured
  nothing in that run.
- `setClient` re-pins `screen.refreshRate` for the new spec, so the hi-res scenario really
  reports 120 Hz.
