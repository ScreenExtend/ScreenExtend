## 1. The keyframe storm (defect, host-side fix)

**What happens.** Every client page that decodes with WebCodecs takes the frames out of an encoded
transform and never hands them back, so libwebrtc's own video decoder never receives a decodable
frame. `VideoReceiveStream2` answers "no decodable frame for 200 ms" with a keyframe request
(RTCP PLI), and keeps doing so for the life of the session. The host funnels PLI/FIR through the
session's `KeyframeGate`, whose same-network window is 200 ms, so it admits nearly every one.

| build | static desktop, 30 s | per 15 s window | host |
|---|---|---|---|
| `06e6fbb` (head) | 117 PLIs | 52–63 PLIs | ~3.6 IDRs/s (`idrs_sent=381` after ~100 s; 1 suppressed) |
| `bef5f89` (old app) | 127 PLIs | 59–62 PLIs | no gate: every PLI logged `RTCP PLI received, requesting IDR` (425 in a 369 s run) |

So the old app had it too (worse: no gate). It is not what makes the head slower than the old
app, but it inflates every measurement: on a mostly static small-window scenario the stream ran at
~5.2–5.4 Mbps, almost all of it IDRs.

**Why the host cannot just drop PLIs.** Nothing in the RTCP packet separates libwebrtc's starving
decoder from a page that genuinely needs a keyframe: the page's own `sendKeyFrameRequest()` also
leaves as a PLI, and the relay's older page and the pre-overhaul page (which cannot be changed)
use it too. A `<video>`-element client's PLIs are always genuine.

**Host-side design (`keyframe.rs::PliBackoff`, wired in the RTCP reader in `webrtc_session.rs`).**
Goes by behaviour instead of origin: a decoder that an IDR fixes stops asking; one that keeps
asking after being answered is not being fixed by IDRs.

- Each answered PLI/FIR that is followed by another doubles a window: 200 → 400 → 800 → 1600 →
  cap 2000 ms. A receiver that never stops asking settles at one IDR per 2 s (was one per ~250 ms).
- A PLI-free stretch of 4 s closes the window: a decoder that asks once in a while is always
  answered at once (subject only to the existing `KeyframeGate`).
- Evidence that a request is real opens the window immediately: a NACK, transport-wide feedback
  reporting a lost packet, or the client's own STATS frame showing its `keyframe_requests` counter
  moved (the page counts every request it makes; ~1 s cadence).
- The client's out-of-band request (opcode 0x64, reliable DataChannel) is not affected — it goes
  straight to the `KeyframeGate`.
- First request of a session is always admitted; the host's own requests (`Connected`, first RTP
  on the wire, lagged viewer) are not affected.
- Suppressions are added to the gate's counter, so `keyframe_requests_suppressed` in telemetry
  covers them.

**Recommendation for G05 (client half).** On a transform path, request keyframes with the
out-of-band 0x64 opcode (host already parses it and advertises the capability bit in the PONG)
instead of `transformer.sendKeyFrameRequest()`. Then every PLI from such a client is libwebrtc's
starvation noise and the host could ignore PLI/FIR completely once the client's STATS say
`transport_tier != 0 && key_tier == outOfBand`. Until then `PliBackoff` keeps the host safe for
every page, including the relay's and the old one. Measured numbers: sections 3 and 4. (G05 has since done the first half differently, see section 9.)

**Who is asking (split by source, as the input report asked).** Host telemetry keeps
`keyframe_requests` (RTCP PLI/FIR plus the 0x64 opcode) and `client_keyframe_requests` (0x64 only;
the summary line omits a counter that is zero). On every head run, `client_keyframe_requests`
never appears, i.e. 0; the page's STATS frame reports `key=sendKeyFrameRequest`. So the whole
storm is RTCP, and the browser's own stats agree: `inbound-rtp.pliCount` 117 in 30 s against a
host `keyframe_requests` rate of ~3.6–3.9/s. The out-of-band channel (`eff862a`) contributes
nothing on Chrome 154.

## Cross-findings for other groups

- **Hi-res runs at constant QP 15 on the head, CBR on the old app (G02/G04).** In the handler's
  standard run the hi-res client is the *second* join of the same browser, so the host already has
  a device override for its token, and `server.rs` (the `if let Some(o) = device_settings` block)
  then sets `cfg.qp = Some(o.video_quality)` = 15 unless `adaptive_quality` is on. Host log of the
  head: 1080p join `rc=cbr, qp=None`; 1440p join `rc=constqp, qp=Some(15)`. The old app
  (`bef5f89`) logged `rc=cbr` for both, at Baseline. QP 15 at 2560x1440 with an IDR every ~300 ms
  (the storm) is a very large stream; it is the first candidate for the hi-res regression the
  baseline agent measured (head p50 40.1 vs old 31.9 ms), ahead of anything per-packet. Not
  measured in isolation by me (rate control is not a G03 file).
- **SCTP delayed SACK (input report lead 3).** webrtc-sctp 0.17.1 holds the SACK for a lone DATA
  chunk for `ACK_INTERVAL` = 200 ms (`association_internal.rs` ~l.1034, `timer/ack_timer.rs`);
  a second chunk, a gap, or the sender's I-bit (`SACK-IMMEDIATELY`) makes it immediate. The ack
  policy (`AckMode`) is `pub(crate)` "for testing", so there is no setting and no patch-free
  switch. A delayed SACK never delays *delivery* of a received message to the application; for
  input (client → host) it only holds back the browser's congestion window, which input rates do
  not approach. **But it does hurt the host's audio sender, through `buffered_amount`:**
  webrtc-sctp counts a message in `buffered_amount` from queueing until the peer's SACK for it
  arrives (`stream::on_buffer_released` is called only from `handle_sack`), so in-flight and even
  delivered bytes count as "buffered". The audio forwarder dropped every packet while
  `buffered_amount` exceeded 40 ms of audio — i.e. for the whole of any delayed-SACK interval. That
  is exactly G06's observation (drop bursts of 41–43 packets ≈ 205–215 ms on an idle link). Fixed
  in commit `07ec295` by allowing one SACK interval (220 ms) of in-flight data on top of the 40 ms;
  UNVERIFIED end to end (request in "Unverified"). Old app: flat 16 KiB threshold, never hit.

- **D-02 (lost `/whep` answer), read-and-reason on the shared runtime.** tokio 1.46.1: a task
  woken onto a worker's LIFO slot cannot be stolen (`worker.rs` l.406: "Except for the task in
  the lifo_slot, all tasks can be stolen"), so anything that blocks a worker synchronously
  strands whatever that worker just woke — an h2 connection task included — for as long as the
  block lasts, however many other workers are idle. What blocks a worker on or near the join path:
  - `server.rs` calls `session.stop()` **inline in async code** on four paths (l.2154, 2188, 2212,
    2226 at `b35b4a0`: a failed handshake, and the three "superseded by a newer offer" stand-downs).
    On Windows that is `WGC control.stop()`, which joins the capture thread — milliseconds normally,
    seconds if the capture thread is wedged (G01 found WGC stuck on a stale monitor handle after a
    mode set). The other stop sites already use `spawn_blocking` (l.1449, l.2316). These four are
    exactly the paths a retried or renegotiated join takes. G04's file: wrap them in
    `spawn_blocking` like the others.
  - In G03's files nothing blocks a worker: `get_stats` is async (measured below), the injector
    join and the link-medium WMI probe are `spawn_blocking`, and every std mutex is held for a
    copy. `broadcast_bye` (`session.rs`) blocks on a std channel for up to its timeout, but only at
    shutdown.
  - A mitigation in the runtime itself (`disable_lifo_slot`) exists only behind `tokio_unstable`;
    not cheap, not done.
  Unproven: no run reproduced D-02 with a stack captured; this is the most plausible mechanism I
  could find, not a diagnosis.
- **Superseded teardown unregisters the live session's telemetry (G04/G08).** Both transports of a
  renegotiated join are registered under one join id; the superseded session's teardown
  (`server.rs` l.2301) calls `telemetry::unregister(&join)`, which removes whatever is registered
  under that key — the *new* session's handle. Before the D-05 fix that happened 15–30 s after the
  edit; with it, right after the new transport connects, so `status --json` loses the session's
  telemetry from the first renegotiation on. Fix: unregister only if the registered `Arc` is the
  one this session published (`Arc::ptr_eq`), the same way `unregister_trickle` now does.

## 8. Questions for the owner

- **Bitrate vs latency on a real link.** The old app ran every session at ~1 Mbps by accident
  (the RTT unit bug). Assumed: the owner wants the picture quality of the full CBR target, with
  congestion control doing its job. If "fast on Wi-Fi" matters more than sharpness, a lower
  default target would cut queueing on a real AP (not measurable on loopback).
- **Keyframe answer latency vs IDR rate.** Assumed: with the page painting via WebCodecs, a
  libwebrtc PLI may wait up to 10 s (the page's own requests are still answered at once). If any
  client page answers decode errors *only* through `sendKeyFrameRequest` without its STATS counter
  moving, that client could wait up to 10 s; G05's page counts every request.
- **Audio drop threshold.** Assumed: up to ~260 ms of queued audio on a truly congested link is
  better than 200 ms holes on an idle one. If the owner prefers holes to delay, lower
  `AUDIO_SACK_ALLOWANCE_MS`.

## 9. Recommendation for G05 (client half) — status

G05 now writes decoded keyframes back to the receiver (PLIs ~10x fewer). The remaining step that
would let the host ignore PLI/FIR outright: request keyframes on transform paths with the 0x64
opcode, and report `key_tier = outOfBand`; the host could then drop every PLI from such a client.
Until then `PliBackoff` + the healthy cap cover every page, including the relay's and the old one.
