### The desktop panel, by reading (`src/components/log-terminal.tsx`, `logbus.rs`, `lib.rs`)

- `logbus::attach` is called on the GUI path only, before the window is built (`lib.rs`), and
  lines logged before it are not lost: the writer puts every line in the ring regardless; only the
  emit needs the handle. Lines from capture/encode/audio threads go through the same `try_send`.
- On mount the panel calls `get_log_backlog` (arms `STREAMING`), then `events.logLine.listen`, and
  on unmount `set_log_streaming(false)`. A webview reload skips the unmount; the next mount re-arms,
  so streaming does not stop after a reload.
- **Race 1 (host, fixed `304cf95`)**: the writer read `STREAMING` before pushing a batch and emitted
  on that stale value; a batch straddling the panel's backlog read was in neither. Now decided under
  the ring lock the panel arms under; test `a_panel_opening_mid_stream_loses_no_line`.
- **Race 2 (UI, open, for the desktop-UI job)**: the panel's `listen` is registered one IPC round
  trip *after* the backlog returns; any batch emitted in that gap reaches no listener. Repro: open
  Settings → Logs during a join (a burst of ~60 lines/s) and compare with `ScreenExtend logs`.
  Fix: listen first, buffer, then read the backlog and drop the overlap — which needs a sequence
  number per line (a `get_log_backlog` / `LogLine` shape change → bindings regeneration).
- **Ring size**: 2000 lines. Measured line rates in 57 earlier handler runs: 0.7–12.5 lines/s
  average, peaks 30–62 lines/s at a join, 0 drops anywhere. The busiest run had 991
  `BWE: RTT congestion signal … clamping` and 335 `RTCP PLI received, requesting IDR` lines (G03's
  keyframe storm and congestion loop): at that rate the join's own lines leave the ring in a few
  minutes. A flood source also exists in input code (below), out of this group's reach.
- **`log::` macros go nowhere**: no `log` backend is installed. Five avatar error paths in `lib.rs`
  fixed (`18311e0`); two in `windows_utils/driver_ipc/sync/client.rs` (G04's) still vanish; and
  everything `webrtc-rs` logs through `log` is invisible by design.

## GUI host vs `serve` host — every difference found (Windows)

Read from code (a separate read-through, checked against the files cited); the GUI itself was not
started (it steals focus on launch: `focus_main_window` calls `SetForegroundWindow` with
`AttachThreadInput`, which can redirect the owner's typing; and it is the later UI job's ground).

**None of these makes the GUI's steady-state streaming slower than `serve`.** Both start the
per-adapter servers through `watch_for_network_changes` → `sync_streamers` →
`Streamer::run_with_handle` → `prepare()`, so the process/thread tuning (HIGH priority class,
`timeBeginPeriod(1)`, power-throttling exemption, GPU scheduling class, MMCSS on transport
workers), the one shared transport runtime and the capture/encode/audio threads are identical.

1. **Process tuning, runtime, DPI** — identical. DPI: tao sets per-monitor v2 before `setup` in
   both modes, so `SetProcessDpiAwarenessContext` fails "Access is denied" on every `prepare()` in
   both (logged; harmless).
2. **Startup order (GUI race)** — the GUI starts its servers (`watchForNetworkChanges`) *before*
   `setSessionCredentials`; for that moment an OTP join is refused (pre-approved tokens get in).
   Disconnect grace is pushed by a separate effect that can land after the servers are up.
   `serve` sets everything first. Low impact.
3. **Audio output pin not restored in the GUI** (`bootstrap.tsx` replay never calls
   `setDeviceAudioOutput`; `serve` does). A device pinned to an output plays on its default after
   a GUI restart. UI-side, medium.
4. **Same `config.json`, different fallbacks for a missing field**: `videoQuality` 23 (TS schema)
   vs 15 (Rust `parse_saved_devices`, `join_defaults`, `Device::defaults`); `remoteControl` false
   (TS) vs true (Rust). Only hand-edited rows lack them. Not changed here: which default is meant
   is a question for the owner (below), and `remoteControl` is input.
5. **Trust learned at runtime is GUI-only**: the GUI calls `setDeviceApproved(token, true)` and
   saves `knownDevices` on every join; `serve` only prints, so under `serve` a device that joined
   must type the OTP again on its next join and is not remembered. Behaviour difference, not a
   latency one; affects how the handler's joins differ from the owner's (every handler join is
   an OTP join).
6. **Blocking sync commands on the UI thread (GUI only)**: `set_server_ports` and
   `set_disable_gpu_encode` call `restart_streamers` on the main thread — up to ~2.5 s of frozen
   window, and every session dropped (5510dc9 claimed the GPU toggle no longer drops devices; it
   still does). Cheap at startup (no sessions yet).
7. **The main thread never pumps under `serve`** (it blocks in `rx.recv()` inside Tauri's `Ready`
   callback), so tao's hidden window never answers broadcast messages. Whether a display-topology
   broadcast waits on it was not verified. `serve`-only; unknown impact.
8. **Extra GUI-process work**: WebView2 (browser/renderer/GPU processes), the compatibility probe,
   the update check, and a Monaco editor warm-up scheduled right after the dashboard appears
   (seconds of renderer CPU that can overlap an early join). Low.
9. **Log bus**: `attach` and `LogLine` emission exist only in the GUI and only while the Settings
   panel is mounted (≤ ~20 batched events/s). Fixed: `ScreenExtend logs` armed it permanently.
10. **`serve`-only**: `-v` echo on every logging thread (now non-panicking); device listeners
    printing on the joining thread; the 5 s telemetry summary under `-v`; `--encoder` /
    `--software-encode`.
11. **Cloud relay** — on by default in both (`publicSessionsEnabled` default true; the handler
    always passes `--no-cloud`). `CloudClient::spawn` builds **its own** multi-thread runtime of
    one worker per logical CPU (16 here), each registered with MMCSS "Playback" at ABOVE_NORMAL —
    the duplication the shared transport runtime was introduced to remove. Idle unless a relayed
    client joins; not on the LAN join path; registration is on its own thread, so it delays
    neither startup nor a LAN join. **Not run** (it would register a public session with
    `session.screenextend.app` on the owner's behalf). This is the one measured-config difference
    between the handler's hosts and the owner's.
12. Control server, exit path (BYE + `remove_all_displays`), STUN/TURN replay — the same.

## Defects found

Fixed on this branch (host side, each with a test or a handler reproduction):

1. `304cf95` logbus emit decision raced the panel's backlog read (lines lost from the panel).
2. `8e4db79` `LOGS` verb armed the panel's `LogLine` stream permanently.
3. `3032603` control replies decoded per 4 KiB read (U+FFFD in `logs`).
4. `18311e0` avatar errors through `log::error!` reached no log.
5. `8423abf` `-v` echo / serve's device listeners / "Stopping…" panicked on a closed pipe.
6. `52c3eb3` `serve` answered `/health` before its control server existed.

Open (outside this group's files, or a UI/packaging change):

- PowerShell does not wait for the GUI-subsystem CLI; exit codes lost (packaging: a
  console-subsystem `ScreenExtend-cli.exe` shim, or document `| Out-Host` / `Start-Process -Wait`).
- Panel listen-after-backlog gap (UI; needs per-line sequence numbers).
- GUI never restores a device's audio output pin (UI).
- GUI starts servers before session credentials and grace are pushed (UI ordering).
- `set_disable_gpu_encode` / `set_server_ports` run `restart_streamers` on the UI thread and drop
  every session (windows_utils/mod.rs; G02/G10).
- **Input-path log flood** (`d3ce813`): `send_inputs`/`inject_pointer` in
  `streamer/input/windows.rs` log every failed `SendInput` with no rate limit (UAC secure desktop,
  lock screen, UIPI). At pointer rates that formats a line per event on the input path and
  evicts the 2000-line ring within seconds — which is also a "logs don't come through" cause.
  Input code is off limits: for the input report.
- `driver_ipc/sync/client.rs` two `log::error!` that reach nothing (G04).
- Cloud client builds a second 16-worker MMCSS runtime (relay; G03/G09 later).
- `cloud_status.lock().unwrap()` (not `lock_recover`) in `register/unregister_cloud_session`.
- `7fa2ebc`: a relayed `/reconfig` with no join id picks `.next()` of a client's joins —
  arbitrary when it has two.
- `57d1620` (macOS): log strings lost their `\` continuations (long runs of spaces).
- `c3780ca`: if the writer thread fails to spawn, every line is silently dropped (`.ok()`);
  queued lines are lost at process exit (no flush on exit).

## Hot-path cost of this group's code

- **Log bus**: one `format!` + one bounded `try_send` per line on the calling thread, always (the
  backlog is always kept); `-v` adds one locked write to stdout/stderr. Measured rate (E1): mean
  0.7–12.5 lines/s, peak 62/s; no per-frame or per-packet line at steady state. Not a latency
  factor in either mode. The handler's `-v` therefore does not make `serve` slower than the GUI in
  any measurable way.
- **Control server**: one thread parked in `accept`; nothing per frame.
- **COM** (E4): no change on streaming threads.
- **Cloud client**: GUI default; a second runtime of 16 idle MMCSS workers (not run; see the GUI
  list, item 11).
- **Network watcher** (79087c4): event-driven; the old 1 Hz WMI + netsh poll is gone.

## Questions for the owner

1. **How do you read logs — the Settings panel, `ScreenExtend logs`, or `serve -v` in PowerShell?**
   Assumed: any of the three. If it is `ScreenExtend logs` in PowerShell, the likely experience is
   output appearing after the prompt (PowerShell does not wait for this GUI-subsystem exe, E3); a
   console-subsystem `ScreenExtend-cli.exe` companion would fix it and is a packaging change, not
   made here. Workaround now: `ScreenExtend logs | Out-Host`.
2. **Which `videoQuality` default is intended for a device row without one: 23 (desktop UI
   schema) or 15 (host)?** Assumed: leave both (only hand-edited rows differ). If 23, the host's
   `parse_saved_devices`/`join_defaults` should change; if 15, the UI schema.
3. **Should a device that joined a `serve` host be auto-approved for its next join, as the GUI
   does?** Assumed: no change (it is a trust decision). If yes, `serve`'s device listener should
   call `set_device_approved` and save `knownDevices`.
4. **Are public (relay) sessions wanted on by default?** The GUI registers one with
   `session.screenextend.app` at every start unless turned off, and spawns a second 16-worker
   runtime for it. Assumed: keep the default; not measured.
5. Is a 2000-line backlog enough? A join plus a few minutes of the current keyframe/congestion
   chatter (G03) fills it. Assumed: keep 2000 and let G03 cut the chatter.
