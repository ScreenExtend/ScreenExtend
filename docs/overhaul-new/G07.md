## 1. The join, broken down to the millisecond

**Head (`exp1`/`exp2`, instrumented, no change), a browser's first join:**

| step | e1-none | e2-1-none | e2-3-none |
|---|---|---|---|
| audio caps probe, worklet, refresh rate (parallel) | 172–178 | 155–166 | 130–136 |
| **output enumeration resolves** (`enumerateBeforeJoin`) | **1697** | **1832** | **1498** |
| `/net-config` (primed), `/ice-config`, transform-worker fetch | +12 | +10 | +9 |
| **`new RTCPeerConnection()`** (long task 489 / 464 / 406 ms) | **2196** | **2305** | **1912** |
| createOffer + setLocalDescription | +9 | +7 | +7 |

**The same build, a later join in the same browser** (slow_answer attempts 2–4): POST leaves at
60–98 ms, the answer at 2.6–2.7 s, first paint 2.76–2.84 s. Everything before the POST is ~60 ms
once the browser has enumerated once and started its WebRTC stack once.

So on a first join **~2.0 s of the client's ~2.2 s before the offer is two first-use costs**: the
first `enumerateDevices()` (1.36–1.67 s here, headless Chrome with fake devices) and the first
`new RTCPeerConnection()` (0.41–0.56 s of main-thread work). After the answer the client is fast:
ICE+DTLS ~10–70 ms, first frame ~80–110 ms after the answer. Nothing waits on ICE gathering (trickle
is on and the offer leaves in the same millisecond as `setLocalDescription`), and the trickle
"settle hold" never held the stage in any run (`iceSettled` always before `rendered`).

## 4. Defects

Found and fixed:
- **D1 (K2)** A lost/late WHEP answer demoted the session to `<video>` for good. Fixed.
- **D2 (K3)** `pagehide` sent no `/leave` when the page was not yet live or was reconfiguring, so
  the display lived ~45 s and the next join made a second one (G04's observation). Fixed.
- **D3 (K1)** First-join offer delayed ~2 s by two first-use costs inside the click. Fixed.

Found, not fixed (with owner):
- **D4 Lost answer itself** (baseline, G04): 10 of 66 first joins and 7 of 63 later joins on the
  head never received their answer; seen on the old app (2 of 10). In `base2` (this ledger's own
  baseline) the host logged the answer 4.0 s after the POST, the browser never got it, the page's
  retry never even sent its POST within the following 27 s (its `/ice-config` fetch did not
  return), and requests flowed again only after the first session's peer connection closed. That
  pattern — every request on the page's one HTTP/2 connection stalled together until a session
  ended — points at the host's connection task not being polled (a tokio task parked behind a
  blocked worker), not at the page; the page's own main thread was idle (no long task in that
  window in the instrumented runs). Not established; G03/G04/host-runtime question. The client can
  only make the retry harmless (K2, K4 + host half).
- **D5 Second display after a lost first answer**: needs the host half of K4 (§5).
- **D6 Stage confusion with two displays** (handler): after the retry, `resolveGdi` picked the
  orphan display ("newest of 2 joins" by list order), so `dropfirst,nodemote` reported no stamped
  picture although the page painted. Handler bug, left for the handler owner.
- **"orientation landscape" costs no renegotiation** in every mined `settings_change` run (portrait
  → landscape revert: 0 new peer connections, 0 gap) while "orientation portrait" costs one. Either
  the revert is correctly a no-op or the host drops it; G04's question.

Investigated, not a client defect:
- **Two epoch bumps in one save** (G04 item 2): the page does apply the second bump — it stops
  polling while rebuilding and the poll restarted by `onStreamLive` sees the newer epoch and
  rebuilds again (harness case 13). The cost is a second in-place renegotiation (1–2 s picture
  gap). Coalesce on the host (one epoch per save), or debounce on the client; neither done.

Settings-change cost on the head (mined, 7 valid runs × 10 classes): every stream-class edit
(quality, video scale, refresh, DPR, orientation→portrait) = exactly 1 new peer connection and 2
`/whep` requests (POST + PATCH), largest picture gap 0.4–1.6 s, picture back in 0.6–2.5 s; audio,
display scale and name = 0 rebuilds. No duplicate session or display on the head. (One G04 run
showed `DUP` on every edit after a quality edit made 3 peer connections; that was G04's own
experiment build.)

## 5. The lost-answer fix: host half (for assignment; not implemented here)

Client half is `e8cbe87`: `attemptId`, 32 lowercase hex digits, minted once per page load, sent in
every `POST /whep` body beside `joinId`. Host half, precisely:

1. `server.rs` `JoinRequest`: `#[serde(default, rename = "attemptId")] attempt_id: String`,
   validated like a join id (`is_join_id_shape`-style: exactly 32 `[0-9a-f]`), else treated as
   empty.
2. `session.rs`: store the attempt id on the session when it is opened
   (`open_session_via(…, attempt_id)` or a `set_session_attempt(s, join, attempt)`), and add
   `pending_join_for_attempt(s, attempt) -> Option<(join_id, device_token)>` returning the join
   opened under that attempt **only while it has never reached ICE connected** (a flag set by the
   peer connection's first `Connected`; G04 knows where).
3. `process_join`, after the OTP (or approved token) check succeeds and **before** a token is
   minted: if `pending_join_for_attempt` answers, use that session's device token instead of
   minting (log "join retried attempt …; keeping its token").
4. `start_session`: `continuing = continuing_join(join_id, token)
   .or_else(|| attempt_continuation(attempt_id, token)) .or_else(relayed_continuation)`, where
   `attempt_continuation` returns the pending join from (2) when its token equals `token`. The
   rest of the continuing path (stop the outgoing capture, reuse the display, `DeviceModify` not
   `DeviceJoin`, the superseded attempt's teardown standing down) is what a renegotiation already
   does after `f789b76`.
5. Security: the attempt id is a 128-bit value sent only over the same request that carries the
   OTP; it is honoured only for a session that never connected and only after the OTP validated,
   so it grants nothing an OTP-holder could not already get, and never a live session.
6. Test: unit test beside `continuing_join`'s; live test `{"scenarios":["small_window"],
   "duration":5,"calibrate":false,"url_params":"g07=dropfirst"}` on a build with the
   instrumentation switch — pass when `status --json` shows one join and the driver one display
   after the retry. Costs 1–2 display creations.

## 7. Modals over a live stage (input-report lead 2)

arms when the host commands a sink the engine refuses, and fires on the user's next tap, which then
leaves fullscreen and drops pointer and keyboard lock. G06's `ba49338` makes it fire only after the
host operator explicitly picks "Choose a speaker on this device…" (`se:choose`). Recommendation
(not implemented; G06's audio logic): a host-commanded sink that the engine refuses should be

the user did not ask for. Input-report lead 3 (first `PING` only after 1 s in `input.js`) is noted

## Addendum 2026-10-05 — a failed join gives everything back (branch `join-failure-restore`)

The owner: "WHEP POST failed: 500 join failed: virtual display 0 did not attach within timeout …
also allow copy etc, disable screen lock, and undo all such items if theres an issue while

### What was left armed, and why

Reproduced by the new full-page case in `test-client-join.mjs` against `59bada3`:

- **No copy, no typing: input.js armed at Connect and never disarmed on failure.**
  `RemoteInput.setup(pc)` runs in `start()` before the offer and sets input.js's `active`, which
  turns on its capture-phase window `keydown`/`keyup` (each `preventDefault()`s), the
  copy/cut/paste forwarders and the stage handlers. The catch's last branch was `showError(...)`;
  only `teardownSession` calls `RemoteInput.teardown()`. So after a refused or lost answer the form
  could not take a key (Ctrl+C on the error text, a corrected OTP) until the page was reloaded,
  and the peer connection stayed open. There is no CSS cause: `user-select: none` is only on
  `#video`/`#canvas`/the stale canvas, and `contextmenu` is suppressed only on the stage.
- **Wake lock, fullscreen, the leave prompt: the `'poll'` outcome.** A renegotiation (epoch bump,
  rotation, demotion) that failed was answered with `reconfiguring = false; startReconfigPoll()`.
  Its peer connection had already been closed by `start()`, so the page showed a frozen frame with
  `isLive` true and `startLock`'s wake lock, fullscreen, pointer/keyboard lock and `beforeunload`
  still held, kept "alive" by `/reconfig` answers. The 15 s reconfigure deadline had been disarmed
  by the same `reconfiguring = false`. This is the route by which a failed connection leaves the
  wake lock on (a first join that fails never reached `startLock`).
- **A third offer.** After the same-tier retry (K2) a second host-side failure fell through to
  `if (s.webcodecsTier) return 'video'`, so the owner's 500 was offered three times.
- `pagehide` sent the beacon and closed the peer connection only; a page restored from the
  back/forward cache came back with everything held. `onStreamLive`'s 450 ms "hide the form" timer
  was not cancellable.

### The inventory, and when each item is now armed and undone

The full table is the comment above `restorePreJoinPage` in `static/index.html`. In short:

| armed | when (now) | undone by |

| input.js data channels | `start()`, before the offer (they are in the SDP) | `teardownSession` → `RemoteInput.teardown` |
| input.js listeners (keydown capture, clipboard, stage pointer/touch/wheel/drag/contextmenu, blur/focus/visibility/pointerlockchange) | switched on by `setup`, **held suspended until `onStreamLive`** (`syncInputGate`); a modal can only add to that | `teardownSession` |
| PING/STATS 1 s interval, `#imeSink` focus | input.js `reliable.onopen` (PING/STATS keep flowing while suspended, by design) | `RemoteInput.teardown` |
| transform worker, canvas transfer, videostats/liveWatch/statsPoll intervals, rVFC loop, transform/frame watchdogs | `start()` / `ontrack` / ICE connected | `teardownSession` |
| trickle sender + 2 s ack timer, ICE settle 8 s | offer / answer | `teardownSession` |
| WHEP 10 s abort timer | the POST | its own `finally`; an in-flight POST is not aborted by a teardown (aborting could cancel the host's handler mid-display-creation), so its timer fires later as a no-op |
| `/reconfig` probe | `onStreamLive` | `teardownSession` |
| reconfigure 15 s deadline | `reconfigure()` | `restorePreJoinPage` |
| `<video>` source, "Tap to start playback" | `ontrack` / `tryPlay` | `restorePreJoinPage` |

| Connect disabled, spinner | submit | `restorePageChrome` |
| microphone card, browser chooser, HTTPS upsell | before the offer only (G06) | their own buttons / bounds |

Arm-late decisions: the wake lock and the leave prompt need no gesture, so nothing justifies them
before a picture. Fullscreen and pointer lock want a user gesture; they still ride the Connect
click's activation when `onStreamLive` lands inside it, and otherwise the next tap (the existing
gesture handler). Arming them at the click instead would hold the screen and the leave prompt over
a join that may never produce a picture. Input forwarding cannot be created late (the channels are
in the offer), so it is created early and *gated* late.

### Changes

- `restorePreJoinPage(msg, keepJoin)`: the one end of a session. `setupFailureAction`'s
  `'error'`, `linkLost` and `kickDevice` call it; `sendLeave` (`pagehide`) calls it with

### The host side of the 500 (read only; not changed)

`server.rs` `start_session` → the create path: `wait_for_new_monitor` polls up to
`DISPLAY_ATTACH_TIMEOUT` (5 s) while `[display] failed to apply extend topology (SetDisplayConfig
win32 error 31)` repeats, then `remove_display_now(client, display_id)` and
`bail!("virtual display {display_id} did not attach within timeout")`; `process_join` maps every
`start_session` error to **500** `join failed: …`. So the failed display is removed before the 500
is sent, and the page's single retry does not leave two displays side by side. It is still a
second create (another ~5 s under `DISPLAY_CORRELATION_LOCK`, and on this machine another slice of
the driver-host leak documented in G04). The page's handling is now right for what it can know:
one retry (a 5xx can be transient: a correlation race, a relay hiccup), then stop, keep the join,
show the host's text. What the host could do better (not implemented):

1. **Say what kind of failure it was.** Every `start_session` error is 500. A display that cannot
   attach because the driver host is exhausted is not transient; a `503` with a machine-readable
   reason (and a retry hint only for the transient kinds) would let the page skip the retry and
   say "the host could not create a display" instead of a raw error string.
2. **Fail fast on error 31.** `SetDisplayConfig` returning `ERROR_GEN_FAILURE` on every attempt is
   known within the first polls; waiting out the full 5 s, holding the process-wide correlation
   lock, delays every other join too.
3. **Surface the driver host's health.** The leak (G04: ~47 MB and +5 threads per attach or mode

### What input.js arms that the page could not undo

Nothing that matters is left: `RemoteInput.teardown()` and `RemoteInput.setSuspended()` were
enough, and input.js is untouched. For the input owner, three things noticed while reading it:

- `reliable.onopen` focuses the off-screen `#imeSink` on a fine-pointer device even while the
  session is suspended, so if the channel opens before the first frame the form's focus moves to
  the hidden input during "Connecting" (keys go nowhere because the gate is closed, and `teardown`
  blurs it). Hook wanted: skip the focus while `suspended`, focus on `setSuspended(false)`.
- `setSuspended(true)` at `setup` sends `FOCUS_STATE false` / `POINTERLOCK_STATE false` into a
  channel that is not open yet; `rawSend` drops them, so the host's first word on focus is the
  `FOCUS_STATE true` sent when the gate opens at go-live (or its default if the channel opens
  after that). Harmless, but the host cannot tell "connecting, suspended" from "never said".
- Listeners installed by `on()` are never removed (they are gated by `active`); correct, but
  "disarmed" there means gated, not detached.

### Questions for the owner

1. **Should a 500 skip the retry?** The page retries any 5xx once (G07 K2). For the attach failure
   that is ~5 s more spinner and one more display create on a host that is failing. Assumed: keep
   the one retry, because a 5xx can be transient and the page cannot tell the kinds apart; the
   host saying which kind (above, 1) is the real fix. One line to change for no retry on 500.
2. **A failed join keeps its join id** (like a lost link), so the next Connect continues on a

   only matters after a lost answer. Assumed right; the alternative is `keepJoin = false` in the
   catch's `'error'` branch.
3. **No cancel button.** While "Connecting" the user can only close or reload the tab. Adding one
   would change how the page looks, which this task may not do; `restorePreJoinPage('', false)` is
   what it would call.
