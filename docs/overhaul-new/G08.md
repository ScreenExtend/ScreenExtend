# G08 — telemetry, probe, tests (measure-only code)

Branch `g08`, from `80e00a4`. Brief: measure-only code must cost nothing on the hot path; the
instruments the other agents trust must tell the truth.

Machine: Windows 11 26200, RTX 3080 Ti Laptop (hybrid), Chrome 154 headless. Every number below
is through `scripts/test-handler/` unless it says "direct". Builds: the integration head binary
`ScreenExtend-handler` (`06e6fbb`, same code as `80e00a4`) and one experiment binary
`ScreenExtend-g08\bin-exp1` (`80e00a4` + temporary `SE_G08_*` switches, **thin LTO, 16 CGUs**;
both arms of every A/B ran on that one binary, so profile is not a variable).

## 2. The total: all instrumentation off vs on

One binary, two arms, interleaved joins, `small_window` + `large_area` at 1920×1080/60 Hz,
`runs: 2` × 20 s per join. OFF = `SE_G08_TELEM_OFF=1` (no `FrameTiming` clock reads, no
histogram records, no summary printer) + `SE_G08_CLIENT_TELEM_OFF=1` (no per-frame worker
stamps/pushes, no STATS frame; the 1 Hz `videostats` poll kept because it is functional).
PING/PONG and every functional counter left on in both.

Per-join p50 (mean of the join's two 20 s windows; ms, stamp metric), arms interleaved in time:

| scenario | ON joins | OFF joins | ON median (range) | OFF median (range) |
|---|---|---|---|---|
| small window 1080p | 26.37, 26.50, 25.39 | 27.55, 27.92 (one window; the other `loaded: true`, discarded), 28.36 | **26.37** (1.11) | **27.92** (0.81) |
| large area 1080p | 30.06, 29.89, 30.71 | 29.95, 31.58, 31.47 | **30.06** (0.82) | **31.47** (1.63) |
| hi-res small window (2560×1440, DPR 2, 120 Hz) | 35.11, 32.55 | 37.33, 35.32 | **33.8** (2.56) | **36.3** (2.01) |

Painted fps: small window ON 52.7–55.3, OFF 53.1–53.9; large area ON 51.9–53.7, OFF 51.4–53.6;
hi-res ON 58.6–59.8, OFF 58.4–59.4. p99 not worse in either direction beyond noise.

**Verdict: the instrumentation has no measurable cost.** Turning all of it off did not make
anything faster; the OFF arm read 1.4–2.5 ms *slower* on p50 in all three scenarios, which I do
not attribute to the instruments (removing work cannot add latency here) — the OFF windows also
ran at higher whole-machine CPU (window means 50–73 % vs 29–62 % for ON; machine shared with
other agents). Unexplained beyond that; recorded as such. Per the brief, the families were not
split further.

Direct numbers that explain why (no display needed):

- Host, copy of `Histogram::record` + `host_now_ns` timed in isolation (`rustc -O`, loaded
  machine): `record` 27–29 ns, `host_now_ns` 46–47 ns, one whole frame's instrumentation (6 stamps
  + 9 records) **0.45–0.49 µs** — about 30 µs per second at 60 fps against an `encode` stage of
  5.8 ms per frame.
- Client worker, per-frame stamps/pushes **0.29–0.39 µs**; the 1 Hz percentile sort 320–350 µs
  before `114cc01`, 77 µs after.

Runs: `on1`/`off1`/`on2` (`small_window`+`large_area`), `off2`/`on3`/`off3` (+ `hires_small_window`),
`on4` (hi-res only), all `runs: 2, duration: 20`, binary `bin-exp1`; every run `ok`, one offer per
join, `cleanup` empty. Memory: started only with commit headroom ≥ 3–6 GB (waited 4–17 min
several times, logged); free physical memory at start 2.3–5.3 GB (off2 and on3 started under
3 GB, above the 1.5 GB suspect line).

Baseline on the integration head (`ScreenExtend-handler`, one join, quiet machine): small window
p50 23.0–26.8 ms, 53.3–54.4 fps; large area p50 29.5–30.3 ms, 50.9–52.6 fps.

## 3. Instruments checked against the truth

| instrument | check | verdict |
|---|---|---|
| WGC `capture_delivery`, `capture_to_encode`, `capture_to_socket` | `SE_G08_TSDIAG`: converted `SystemRelativeTime` minus callback entry, 24 blocks × 120 frames | **lying → fixed (`3120abf`).** Stamp is 3–14 ms *in the future* on 2,879/2,880 frames (block means 8–11 ms); ≈37.7 s off interrupt time, so it is QPC-based but a target present time. Effect in a 200 s head session: `capture_delivery` n=3 of ~9,900 frames, `capture_to_encode` n=1,087, `capture_to_socket` n=1,287; survivors biased (`capture_to_encode` p50 1.05 ms vs `encode` alone 5.77 ms) |
| "`capture_to_encode` p99 ≈ 503 ms early in a session" | same data | **artefact** of the above: only stale (past) stamps survived, and the histograms are cumulative for the session, so a few early stale frames owned the p99. Gone with `3120abf` |
| `encode` stage | reading `ring_keepalive` | **lying for keepalives → fixed (`e96fe2c`)** |
| `idrs_sent` vs what was sent | experiment counter of SPS-carrying access units written to the socket | **truthful**: 241 = 241 in one session (counter not kept, verification noted in `docs/TELEMETRY.md`) |
| `idrs_sent` / `keyframe_requests` vs log | head session: 583 IDRs, 586 requests, 1 suppressed over ~200 s; Chrome `pliCount` 59 in the first window | consistent; it is the keyframe storm G03 owns (≈3 IDR/s) |
| page `hostToPaint` vs handler stamp metric | same windows, quiet machine | offset **not constant**: stamp p50 − `hostToPaint` p50 = 7.1–10.8 ms (small window), 11.3–14.3 ms (large area). The page's number starts at `ReadyMsg.capture` (after the ring copy/scale), so it excludes stage draw → DWM compose → WGC delivery, which varies with scene. Both are fine for A/B within a scenario; do not compare across scenarios via a fixed 10 ms |
| RTP clock origin differs by path | reading | ring path stamps the RTP time **after** the GPU copy/scale (`ReadyMsg.capture`), classic path at callback entry: ~0.13–0.3 ms (the `scale` stage) apart. Not changed (G01/G03 file, affects A/V sync); documented |
| old app's impossible RTT (22–79 s) | webrtc-rs 0.17.1 `calculate_rtt_ms` returns ms; the old driver multiplied by 1000 | unit bug, fixed by `f5d0e27` (G03). The old readings were 22–79 **ms**. The current host surfaces no RTCP RTT in telemetry (only the client's PING/PONG `rtt_ms`, 0.5 ms here) |
| dropped-frame counters vs stamps skipped | `frames_skipped_cadence` 204, `frames_dropped_*` 0–2 in a 200 s session; handler `skippedStamps` per window | no contradiction found; the cadence skips are the gate doing its job (G01) |
| client `decode` | named "decode submit → paint" in `TELEMETRY.md`, `decode_ms` in `status --json` | truthful but the JSON key is shorter than its meaning; left |

## 4. Tests

Gates on the final tree (`114cc01`): `cargo fmt --check` clean; `cargo clippy --all-targets -- -D
warnings` clean; `cargo test`: **464 passed, 0 failed, 18 ignored** (lib), doctests 4 ignored —
run under the handler's measurement lock so the GPU encoder tests could not overlap another
agent's timed window; `pnpm test:client` all 8 harnesses pass (one new case); `node
scripts/check-legacy-webkit.mjs` clean.

- No test printed `SKIP` on this machine (it has the hardware); none was excluded by name.
- Slow: `windows_utils::streamer::test::nvenc_encoder::nvenc_pipelined_submit_is_not_faster_than_submit_and_drain`
  runs over 60 s (whole lib suite 82 s).
- Bare ignores remain on 4 doctests (`driver_ipc` `find_id` ×2, `windows_capture::frame` ×2):
  they print a bare `ignored`, against the convention's spirit; not changed (vendored / G09 files).
- Verify nothing on this machine by design: `report_*` tests are `#[ignore]` read-only reports;
  `bench_push_line` and the packetizer A/B are benchmarks, not assertions.

- Skip convention: hardware/driver tests use `test_support::skip` or `#[ignore = "<reason>"]`;
  the display-creating tests in `windows_utils/virtual_display.rs` are all `#[ignore]` with
  reasons. No test is excluded by name.
- Not run (input injection, forbidden): `scripts/measure-input.ps1`, `scripts/measure-stream.ps1`,
  `scripts/test-startup-gate.mjs`; the `#[ignore]`d input harnesses. For the later input job.
- Commits in this group that are **not** measure-only (misfiled; owners named):
  `3e6e6b9` "docs+test" changes keyframe answering — every client PLI/FIR/out-of-band request
  bypasses LTR repair (`request_keyframe_for_client_quietly`) and a keyframe is forced at the
  first RTP write (G03). `cabf63a` "fix(measure-input)" widens the cursor cadence window ½ → ⅔
  period (G01). `e9f5876` "fix(harness)" gates the host cursor overlay on `cursor_toggle` (G01).
  `d91d2dc` changes `devices list` / control-server output (G09/G04).

- Host instrument costs on a slow host CPU; AMD/Intel/macOS paths (macOS `clock.rs` already gates
  future stamps; not touched).

  '{"scenarios":["static"],"static_duration":30,"host_env":{"SE_G08_TELEM_OFF":"1","SE_G08_CLIENT_TELEM_OFF":"1"}}'`
  against the same request without `host_env`, interleaved ×3.

  final tree (display budget); they change only which samples the histograms keep. To confirm:
  build `g08`, run `{"scenarios":["small_window"],"runs":1,"duration":20,"custom":{"js":"1","host_commands":[["status","--json"]]}}`
  and check `capture_to_encode.count` ≈ captured frames and `capture_delivery` absent.

  directory as `exp1-full.patch` and its binary in `shared_target\ScreenExtend-g08\bin-exp1`.
