## The owner's two complaints

### "Sound doesn't work" — every route to silence, ranked by evidence

1. **Plain-HTTP joins — the LAN QR code is `http://`** (`src/lib/utils.ts` builds
   `http://<addr>:<port>/?id=…`). No secure context means no `AudioDecoder`/`AudioWorklet`, so the
   page takes the standard Opus track — the tier that concealed over half the audio, lost most
   clicks and ran 350–600 ms late (`no_audio_decoder` tier: 5/15 clicks, 627,600 concealed
   samples). **Defect, fixed `201a981`.** This is the strongest candidate for the owner's report:
   it is the default join route, and on it the sound was mostly synthesised. The handler's own
   `plain_http` tier could not complete a join in either build (the `/whep` POST was aborted,
   `net::ERR_ABORTED`, after the HTTPS-upsell modal — G07's area), so the HTTP case is proven
   through the identical track path with `AudioDecoder` removed, not on HTTP itself.
2. **Audio is off by default per device** (TS schema/bootstrap/apply-config `false`, Rust
   `unwrap_or(false)` in `audio_enabled_now` and `parse_saved_devices` — consistent; the old app
   was the same). A user who never opens the device sheet hears nothing. By design → question 1.
3. **A mid-session fast-path failure was silence for the session** (spare track never fed).
   **Defect, fixed `736f0f9`.**
4. **Same-machine join, unmuted browser: an endless echo.** **Defect, fixed `24f75e8`.** Only
   when testing on one machine.
5. **Stale saved output id**: audio kept playing on the default output but restarted ~1×/s.
   **Defect, fixed `61da27a`** (glitching, not silence).
6. **GUI host does not restore a saved output** (G09's lead, traced in code, not run — the GUI is
   out of scope): `src/pages/bootstrap.tsx` replays `setDeviceOverride(…, systemAudio)` per saved
   device — so a device saved with audio **on does get audio** on a GUI host without re-toggling —
   but never calls `setDeviceAudioOutput`; `serve` does (`apply_saved_devices`). Result: after a
   GUI restart the device plays on its *default* output until the sheet is saved again. Not
   silence. **UI defect, open** (reproduction below; the fix is one call beside the existing one).
   No host-side half to fix: the host applies whatever it is told.
7. **Field fallbacks** for a row missing a field (G09's lead): `systemAudio` false on both sides;
   `audioOutputDeviceId` `""` (TS) vs `None` (Rust) both mean the default output. **No mismatch.**
8. **`AudioContext` suspended without a gesture**: the context is built and resumed inside the
   Join click (`beginFromGesture`), resumed on `visibilitychange`, and survives auto-rejoin.
   Headless runs use `--autoplay-policy=no-user-gesture-required`, so a real-browser suspension is
   **not reproducible here**; `degraded` bit 7 reports it. Unverified (reproduction below).
9. Enabling audio needs no renegotiation (the DataChannel/track is always in the answer and the
   forwarders poll the toggle); the *first* `--audio on` for a device with no saved row creates a
   full override row and bumps the stream epoch once (picture rebuilt 1–2.5 s) — G04's table.
10. The old app: the host sent audio but the page could not play it (worker scripts without COEP,
    fixed at `8db3887`). Already fixed before this job.

state — it cannot trigger or pre-empt the microphone logic). `se:choose` is the only door to
non-default outputs on such browsers; the iOS earpiece hold (no `audioSession` category) asks for
the microphone only when the host picks the earpiece.

**Functions changed in G07's `index.html`:** the join `submit` handler (no join-time chooser, no
card, no wait on the enumeration), `applyReconfig` (answers `se:choose`; a refused sink is

## D-13: the ~−65 ms A/V residual (audio trailing the picture)

The page's sync log reads `target=10 ms residual≈−35…−70 ms` in every run: the jitter buffer is
already at its 10 ms floor and audio still trails video. E4 locates it: of ~95 ms from the host's
speaker to the client's audio graph, ~75–80 ms elapsed before the endpoint-loopback capture even
had the sound; network, decode and the 10 ms ring are ~10–15 ms; headless Chrome then adds its
own 52–57 ms output latency (`baseLatency + outputLatency`, the browser's floor). What our side
can do and did: **process loopback (−29 ms, kept)**. What it cannot: the browser's output latency
(`latencyHint: 'interactive'` is already the lowest standard hint; a numeric hint below the
device period is clamped by Chrome), and buffer-target changes cannot help because the target is
already at its floor — lowering `MIN_TARGET_MS` below 10 ms would trade underruns for at most
~5 ms and was not tried. `outputLatency` is already compensated in the target. So: of the
residual, ~29 ms was ours and is gone; the rest is the Windows mix before loopback plus the
browser's output path.

## SCTP (G03's delayed-SACK note) and the audio DataChannel

The audio DataChannel is unordered, `maxRetransmits: 0`, host → client; webrtc-sctp's delayed
SACK applies to what the *host receives*, while the host's audio sender depends on the browser's
(usrsctp) SACKs. Observed in host logs: backpressure drops (`dc_drops`, buffered amount over
40 ms of audio) **in bursts of 41–43 packets ≈ 205–215 ms** (one run: 0 → 2 → 32 → 43 within
4 s; others 2, 41, 42, 43, 120, 125; one other agent's run 1,552), never `lagged`. A ~200 ms
sender stall is what a 200 ms delayed acknowledgement would produce, but this is **not
established** — it needs G03's SCTP trace. Each burst is a ~200 ms audio hole with a
discontinuity resync on the client; the click metric did not catch one (15/15 in those runs).
Latency is bounded by the drop policy (40 ms), so the effect is holes, not delay.

### What auto-detect can do — measured, and what is only documented

**Measured** here, with no ScreenExtend host and no display: a local page on
`http://127.0.0.1` (a secure context) in fresh headless profiles, permissions set with
`Browser.grantPermissions`. Chrome 154.0.8037.93 and Edge 154.0.4258.53, each with the
machine's real devices and with `--use-fake-device-for-media-stream`. This machine has two real
speakers (Realtek, Boom Audio).

| grant | `audiooutput` entries | ids | labels | `query('microphone')` | `query('speaker-selection')` |
|---|---|---|---|---|---|
| nothing | **1** (both browsers, real and fake devices) | **`""`** | **`""`** | `prompt` | throws `TypeError` |
| `speakerSelection` only | 4 real (`default`, `communications`, 2 devices) / 3 fake | all set | all set | `denied`* | throws |
| microphone (`audioCapture`) | 4 / 3 | all set | all set | `granted` | throws |
| both | 4 / 3 | all set | all set | `granted` | throws |

\* `Browser.grantPermissions` denies every permission it is not given; a real profile would say
`prompt`. `selectAudioOutput` is `undefined` in both; `setSinkId` exists on `AudioContext` and on
media elements. The first `enumerateDevices()` of a profile took 0.3–1.5 s, the second 0–17 ms.

**Cached ids are not a way round it** (measured, both browsers): ids read under a microphone
grant, then `Browser.resetPermissions` and a reload: the enumeration is back to one empty entry,
and `setSinkId(<cached id>)` fails for every non-default id (`NotFoundError` on `AudioContext`,
`SecurityError: No permission to use requested device` on an element); re-granting makes the
same id work again. So a list cached from an earlier grant cannot be routed to once the grant is
gone, and the page does not cache one.

**Documented, not tested here:** Firefox lists no `audiooutput` until `selectAudioOutput()` or a
microphone grant, and has `selectAudioOutput()` (116+) as a permission-free chooser; Safari has no
`audiooutput` enumeration before 18.4's `setSinkId`; no shipping Chromium has UI that grants
`speaker-selection` (it is reachable through DevTools and enterprise policy only).

**So, against the owner's expectation:** on desktop Chrome and Edge, auto-detect without a prior
microphone grant yields **no routable output and not even a count** — the single empty entry is
the same whatever is plugged in, so "skip the card when the default is the only output" cannot be
detected either. Under the rule as given, **the card appears at the first join of every Chrome /
Edge profile that has never granted the microphone to that origin.** What makes it less
intrusive, implemented: it is raised **at most once per device** (any answer — a lasting grant,
a one-time "Allow this time" grant, Skip, a refused prompt — is remembered in `localStorage`, and a
lasting grant makes every later join detect without asking); never where it cannot help
(`denied`, no secure context, no `getUserMedia`, a picker engine); and only the host operator
choosing "Choose a speaker on this device…" raises it again, once.

### The decision (`SEAudio.outputPlan`, pure; `prepareOutputsForJoin` runs it)

| case | action |
|---|---|
| no `setSinkId` at all | none |
| ≥1 routable id without asking (labelled or not) | **report** it, show nothing |
| `selectAudioOutput()` engine, operator has not asked | none (host gets the choose entry; never the microphone) |
| `selectAudioOutput()` engine, operator asked | **picker** — the browser's chooser, opened synchronously from the Join click |
| no secure context or no `getUserMedia` (plain HTTP) | none |
| microphone `denied` | none |
| microphone `granted` and still nothing listed | none (asking cannot help) |
| card answered on this device before, operator has not asked | none (`asked-before`) |
| otherwise (Chromium with no grant) | **card**; Continue → the browser's prompt, the outputs are read under the grant and the track stopped at once |

Every input is a non-prompting call: `permissions.query('microphone')`,
`permissions.query('speaker-selection')` (a throw there is an answer, not counted as suppressed),
one `enumerateDevices()` (warm, thanks to `warmJoinPath`). The result is in
`SEAudio.getSyncInfo().outputPlan` / `SEAudio.getOutputPlan()` (action, reason, both permission
states, routable before/after, the card's answer). It is not in the `OP::STATS` frame (that
needs a host field); the existing `degraded` bit 9 still says "labels unavailable", and every
new catch calls `note()`.

### Where the wait sits, and why nothing can expire behind it

(a) **In the submit handler, before the offer.** Order: `beginFromGesture()` (the
`AudioContext`, inside the click, before any await — iOS needs it there) → on a picker engine
with an operator request, `pickOutputBounded()` synchronously (it needs the click's activation) →
Connect disabled → **`await SEAudio.prepareOutputsForJoin(micCard, pickerDone)`** → `joinData`,
the loading state, the capabilities probe, the audio-prepare race (`AUDIO_PREPARE_DEADLINE_MS`,
2 s) and the refresh-rate deadline → `beginStreaming()` → `start()` → `POST /whep`. The host
therefore builds no session and no display for someone reading the card, and the 10 s answer
deadline, the same-tier retry and the ICE settle deadline are all armed later, inside `start()`.
The only timers running during the wait are `warmJoinPath` (already done), the page-load
refresh-rate sampler (its deadline is applied after the wait) and the chooser's own 15 s
`PICKER_DEADLINE_MS`, which ends the wait rather than failing the join. Checked by
`test-client-join.mjs` (prepare is awaited before `beginStreaming`, both deadlines and the loading
state; the chooser is opened before the first await; Connect is disabled first).

(b) **It cannot strand the page.** The card always has Skip, which resolves the wait; a refused
or dismissed browser prompt resolves it (`getUserMedia` rejects); a `showCard` that throws
resolves it as skipped; the enumeration is bounded at 3 s (`ENUM_TIMEOUT_MS`); the chooser at
15 s. Unit-tested: with the card up the preparation is still pending and no `getUserMedia` has
run; Continue resolves it; Skip resolves it; with no `localStorage` at all Skip still resolves it.

(c) **Everything the page can raise, and when:**

| UI / permission | when, before this change | now |
|---|---|---|
| compatibility card, same-device card | page load | unchanged (before the join) |
| HTTPS upsell | page load; and in `beginStreaming` on HTTP without WebCodecs | unchanged (both before the offer) |
| microphone card | only on the operator's `se:choose`, over the live stage | **before the offer only**, from the Join handler |
| browser output chooser (`selectAudioOutput`) | on the next tap of a live stage after `se:choose` | **from the Join click only**; the tap-to-open picker (`queueOutputPicker`) is removed |
| `getUserMedia` for the iOS earpiece hold | when the operator picks the earpiece on iOS < 16.4 | **unchanged — cannot move**: holding the microphone *is* the routing mechanism and must last as long as the earpiece is in use; iOS Safari's grant does not survive a reload by default, so asking at the next join would not hold it; and an iPhone has no fullscreen or pointer lock for it to drop. It is the operator's explicit request. |
| fullscreen, pointer lock, keyboard lock | `startLock()` when the stream goes live; re-entered on the next tap | **unchanged — cannot move**: they belong to the live stage (the element must hold the picture), and fullscreen and pointer lock need a user gesture. The first request still rides the Join click's activation (Chrome keeps it 5 s); after a long card wait it can lapse, and then the stage starts in viewport mode and the next tap enters fullscreen — the existing gesture handler. A modal is now never open when this happens. |
| wake lock / NoSleep video | `startLock()` | unchanged: no prompt (the Wake Lock API is granted to a visible page; the shim is a muted clip) |

## Addendum 2026-10-05 (2) — "can't switch speakers", then the owner's discovery spec (branches `audio-outputs-supported` → `audio-discovery`)

`device.audioOutput.unsupported`, rendered by `device-details.tsx` for `supported === false`. The
owner then replaced the narrower fix with a full specification
(`findings/overhaul-new/OWNER-SPEC-audio-discovery.md`), implemented here.

### What triggered it on the owner's machine

The log does not say: the desktop app (pid 94752) had already closed (`screenextend.exit`: the
window was asked to close) when this work began, and the log bus is in memory only. What the
owner's `config.json` shows (read only): the only device row with System audio on is an **iOS**
device (`172.16.11.91`), and the most recently seen device is a **Windows** browser joined
**through the cloud relay** (its address label is a relay client id). Either fits a root cause
below; which one the owner opened is not recorded anywhere.

### Root causes (`c4ffe6d`)

1. **Host default (most likely):** `AudioOutputsReport` derived `Default`, so `supported` was
   `false` whenever the host had not been told — `session.rs` `audio_outputs_report` /
   `device_audio_outputs_report` (`AudioOutputsReport::default()` / `best.unwrap_or_default()`),
   and `DeviceSessionState::audio_outputs_supported: bool` defaulting to `false`. The sheet calls
   `get_device_audio_outputs` when it opens, so it read "can't switch" for a device that was
   offline, for a join that had not posted yet, and **for every relayed join**: the relay does not
   tunnel `/audio-outputs` (`cloud.rs` `dispatch` answered it 404), so a relayed device never
   reports at all. `server.rs` also read a body without the field as `false`
   (`#[serde(default)] supported: bool`).
2. **Plain HTTP:** the LAN QR code is `http://` (`src/lib/utils.ts`). On an insecure origin
   Chrome 154 hides `navigator.mediaDevices` and `AudioContext.setSinkId` (measured by the
   handler below; `HTMLMediaElement.setSinkId` stays exposed), and `audio.js` required
   `enumerateDevices` for `canSink` (`supported = canSink || canCategory`, line 268 at
   `c4ffe6d`), so it posted `false` for any desktop browser whose user dismissed the HTTPS offer.
3. A post made before `initSpeakers()` carried the initial `false` (minor).

Chromium with nothing granted, a skipped card or a denied permission already posted `true` with
the choose entry before this work; those were not causes.

### Fix

`db377a1` (host + page) and `6cce67c` (host): the session keeps `Option<bool>`; unreported is
`true` with no outputs (the sheet's "Waiting for this device…"); a reported `false` outranks an
unreported sibling join; a body without the field no longer means `false`; the relay dispatch
accepts `POST /audio-outputs` if the relay ever forwards it; one `[audio-outputs]` log line per
post. Page (`db377a1`, then `6c0e363`): `supported` is any sink API (`setSinkId` on a context or
element, `selectAudioOutput`), the iPhone category, or an insecure context. **`supported: false`
is now reachable only on a secure page with no sink API of any kind** — Safari before 18.4 on a
Mac or iPad (an iPhone gets Speaker / Earpiece). That is the honest case and the message is kept
for it.

### The owner's discovery spec (`6c0e363`, `6cce67c`)

Implemented as written, in `audio.js` (`startPicker`, `prepareOutputsForJoin`, `bounded`,
`classify`, `enumerateOutputs`, `primeWithMicrophone`, `listFrom`, `buildOutputs`) and the
`joinForm` submit handler: the chooser is started synchronously in the click; then the
speaker-selection and microphone queries, the enumeration and the four presence probes, each
recorded; the card only when nothing routable came back; `getUserMedia` once, one more
enumeration, every track stopped; default-only (`[{id: "", label: "Default output"}]`,
`labelled: false`) when that fails too. The report is final before the offer. `discovery` is in
the body, on the host (`AudioOutputsReport.discovery`, `status --json`
`telemetry.joins[].audioOutputs`) and in `docs/TELEMETRY.md`.

Deliberate readings of the spec, each a question below:

- **The post goes out at the answer, not before the offer.** The spec's sequence has
  `await postOutputs(...)` before `sendOffer()`, but the host has no session to attach a list to
  until `POST /whep` has minted the join id, and it will not guess one. What the page guarantees
  instead: discovery is complete and the body fixed before the offer, and it is posted as soon as
  the join exists (the test asserts both, and that nothing is posted before the join).
- **The card is not raised where a grant cannot help:** a microphone permission already `denied`
  (`getUserMedia: denied`), no `getUserMedia` (`unsupported`, e.g. plain HTTP), or no sink API to
  route a list (`unsupported`, e.g. Safari before 18.4). The spec's "only if every API failed"
  is kept; these are cases where raising it would ask for the microphone for nothing.
- **The card is raised at every join where discovery fails** (the spec has no memory). The
  earlier "at most once per device" (`micCardAnswer`) is gone, so a Chrome profile that skipped
  the card sees it again at its next join.
- **"Choose a speaker on this device…" is no longer offered**: the spec's report is the full
  list or the default alone. A host row that still saves `se:choose` is ignored by the page.
- **A routable output from any source ends discovery** — the presence probes (APIs 5–8) are
  recorded, not counted as discovery successes, matching the spec's sequencing code
  (`listFrom` → card only when empty) rather than the literal "APIs 1 through 7 all returned
  something other than `ok`", which would never raise the card in a Chromium browser.
